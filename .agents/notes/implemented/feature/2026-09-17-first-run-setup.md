# Agent Note: 无配置首次启动与管理页初始化

Status: implemented

## Problem

手工部署要求操作者先准备真实敏感 TOML 和两个站点 origin。首次部署需要在无配置状态进入
管理页，先输入数据库、管理员、基础和进阶参数，再生成对应配置并继续部署。正常 Admin 启动
会先读取角色 TOML、数据库和 runtime 文件，因此不能仅在已有管理路由加一张表单；配置缺失时
业务状态根本无法装配。

独立设置入口继续由本文拥有，配置模板与发布内容的收敛见
[发布包范围决定](../simplification/2026-09-18-release-artifact-scope.md)。文档重建笔记只规定
文档门禁，没有功能重叠。
数据库的五项输入、编码和兼容边界由[连接参数决定](2026-09-18-database-connection-fields.md)拥有。

可选合并入口的首次确认后初始化和显式 HTTPS 代理由
[单文件 supervisor 决定](../architecture/2026-09-20-unified-server-supervisor.md)部分扩展；
以下分体 Admin 的保存后退出、禁止覆盖与未知结果保护理由仍保留。

## Decision

`auction-admin-api` 在无参数、无显式 `AUCTION_CONFIG_FILE` 且没有现有角色配置时，先于
`AppConfig` 装配进入一次性初始化模式；已有或显式指定但损坏的配置始终失败关闭。默认路径使用
`symlink_metadata` 区分明确缺失、现有条目和探测失败；目录或悬空链接不再被 `is_file()` 当作未配置，
权限等元数据错误直接阻止启动。发布制品也可
通过 `setup --output-dir <绝对路径>` 指定配置输出目标。初始化进程仅监听
`127.0.0.1:8091`，终端打印高熵一次性令牌；普通 Admin HTTP 不注册 `/setup` 或初始化 API。
管理端 Dioxus `/setup` 页面不经过业务会话外壳，初始只显示一次性部署码（终端设置令牌）输入。
先以无请求体的 `POST /api/v1/setup/verify` 独立验证 `x-setup-token` 与完成状态，收到 `verified`
后才显示数据库五项参数、管理员账号密码、两个精确 origin 和有限的基础/进阶参数。
部署码验证不访问数据库、不写文件、不消费令牌，也不建立全局解锁或免鉴权会话；配置校验和保存
每次仍携带令牌并由服务端独立鉴权。页面内存保存部署码和验证状态，刷新后重新验证；错误或
网络异常不进入第二步；后续 `setup_auth` 清空部署码、数据库密码、管理员密码及确认值后退回
第一步，保存成功也清空这些值并隐藏表单。

页面编排留在 `operations/setup.rs`，内存草稿、校验、控件和配置提交分别由
`operations/setup/{draft,validation,fields,form}.rs` 拥有。数字保留原始文本，不在解析失败时沿用
旧值；检查与保存都先走同一校验入口。数据库、管理员和基础分组始终可见，进阶分组默认折叠，
有错时自动展开；字段说明、可定位错误摘要与请求进度都有五语言文案。密码确认只存在于草稿，
不加入 DTO；浏览器只检查可明确表达的格式/范围/字节边界，EnvFilter 语法及完整配置合法性仍由
配置 owner 判定。修改输入清除上次检查结果，检查通过不表示已经保存或完成运行验收。

三个接口使用同一浏览器传输实现，每次请求各有 10 秒总预算，不合并计算三个步骤，也不自动
重试。保存超时、断连或响应无法识别时以 `setup_outcome_unknown` 保守分类；任一初始化接口收到
该码后，页面清空部署码和全部密码，锁定输入、部署码验证、检查和保存。`outcome_unknown` 由页面
持有，配置组件复用同一 signal；提交回调也读取它，不只依赖按钮 disabled。结果不确定提示保持
可见并随当前语言翻译，不被输入或重渲染清除，页面不提供重试/解除入口。该锁只存在于当前页面
内存；操作者必须先停止初始化进程并核对目标目录，不能刷新后直接重试。取消浏览器等待不代表
服务端取消落盘，客户端保守分类不新增服务端 wire 状态，也不代替服务端的终态与禁止覆盖。

`auction-setup` 拥有独立 HTTP 门禁和数据库连通性检查。三个接口先独立鉴权，再竞争同一非阻塞
操作锁；锁覆盖数据库等待与目录发布，竞争返回 `setup_busy`，不积压连接检查。该锁同时持有
`Pending`、`Completed`、`OutcomeUnknown` 状态，保存成功后拒绝新请求；发布后持久化确认失败
则保持不可逆的结果不确定终态，后续已鉴权请求统一返回 `setup_outcome_unknown`，不再校验或
写入。操作者停止进程并核对目录前不能用重新验证部署码解锁；停止该进程不会返回成功退出。

`auction-config` 从通用配置模板物化三角色、公共、敏感和共享 runtime TOML，并让三个角色的
正式 loader 校验完整目录。输出先写在同一受信父目录的临时目录中；临时根和 `runtime/` 分别以
`0700`/`0750` 创建，umask 只可进一步收紧，避免先创建再 chmod 的权限窗口。发布前同步文件、
`runtime/`、临时根目录，再经 Linux `RENAME_NOREPLACE` 发布并同步目标父目录。目标元数据读取
失败不能当作不存在，已有条目（包括悬空链接）拒绝覆盖；发布前失败只清理本次临时名称，发布后
父目录同步失败保留目标并返回 `OutcomeUnknown`。目录仍须受信且不被并发替换，这不是恶意父目录
下的路径竞态隔离机制。数据库连接检查不建库、不迁移，敏感输入与底层错误不进入响应或日志。操作者以实际服务账号启动
初始化二进制，准备运行目录、用户组和 unit 后执行严格部署预检；数据库迁移、启动顺序和
readiness 继续由 `auctionctl deployment` 拥有，Caddy 仍须人工审阅和 reload。

## Alternatives considered

1. **在正式 Admin router 增加未认证 setup 页面。** 复用路由和监听最少，但普通服务会暴露新
   写入口，且无配置时仍无法构造业务状态；故采用独立初始化表面。
2. **让安装器通过 shell 提示输入全部字段。** 不需新 Web 页面，但无法满足管理页设置需求，
   复杂进阶参数和错误恢复也会退化为终端脚本。
3. **自动创建 PostgreSQL 数据库并在保存时迁移。** 看似更一键，但需要高权限数据库凭据，
   且会把不可逆迁移混入可重试的表单提交；因此只做连通性检查，迁移仍归部署控制器。
4. **允许初始化覆盖已有配置。** 可复用表单作重配置入口，但会破坏已部署密钥、runtime
   指纹和回滚证据；现有配置修改继续走受认证的管理页及受控运维流程。
5. **复用完整配置校验接口验证部署码。** 可少增加一个入口，但必须先录入全部凭据且会触发
   数据库连接，无法提供独立的前置验证步骤；因此使用无配置负载、无持久化副作用的独立接口。
6. **只隐藏配置表单或设置服务端全局已验证标志。** 实现简单，但前者不能验证部署码真伪，
   后者会把一个客户端的授权扩散给其他请求；因此前端显式等待验证成功，后端仍逐请求鉴权。
7. **仅依赖原生表单校验与服务端统一错误。** 可以避免浏览器维护格式提示，但检查按钮可能
   绕过提交校验，折叠字段的原生错误也难定位；因此两种动作共用 Rust 校验，并保留服务端权威判定。
8. **保存断连时沿用普通网络错误并允许自动重试。** 可以减少特殊分支，但响应丢失时配置目录
   可能已经发布；因此有界等待后提示人工确认，不把未知结果解释为未写入。
9. **仅给保存加互斥锁，其他接口继续检查。** 可并行检查多个候选，但检查可能在保存成功后
   仍返回有效，结果不确定后也能反复连库；因此三个接口共享门禁与终态，宁可要求等待或人工核对。
10. **前端只提示结果不确定，保留手动重试按钮。** 操作者可快速重试，但响应丢失时原请求可能
    仍在落盘，反复点击会掩盖未知结果；因此当前页面锁定动作并清空凭据，恢复必须先人工核对。

## Consequences

新主机可以在不准备任何 TOML 的情况下打开本机管理设置页并生成完整配置；保存后由操作者
执行既有严格预检与启动链。代价是首次部署仍需预先创建 PostgreSQL 18 数据库/应用账号，远程浏览器
需 SSH 隧道，Caddy import/reload 和目标主机备份仍由操作者负责。两步表单避免先填写完整配置
才发现部署码无效，代价是增加一次独立验证请求，刷新后需重新输入。页面只提供高频初始参数；其余
非敏感高级运行配置由正式 Admin `/config` 页面在登录后编辑。已存在配置、显式路径错误和无
`postgres,web-embed` 的制品不会自动开放初始化。当前只执行静态门禁与发布构建，没有创建真实
数据库、运行行为测试或声称线上验收完成。字段提示让操作者在发起数据库请求前定位输入问题，
代价是浏览器边界、配置层边界和五语言帮助需要同步维护；日志语法不在 WASM 重复实现。令牌
失效时放弃所有密码草稿，牺牲少量重填成本以缩短敏感输入的保留周期。共享门禁消除进程内检查与
发布的交错，代价是并发验证也可能返回忙碌；目录逐层同步增加少量 I/O，不能据静态编译声称已经
验证断电恢复或特定文件系统的持久化行为。前端锁定防止在同一页面重复提交不确定操作，代价是
即使断连发生在请求发出前，也必须由操作者核对并重新建立设置会话，而不能无条件重试。

## Verification

本轮执行格式、文档/仓库策略/布局/配置示例/i18n 静态门禁、工作区 `cargo check --locked
--workspace --all-targets`、`cargo clippy --locked --workspace --all-targets --all-features --
-D warnings`，以及 Admin WASM 的 check/Clippy 和 `auction-admin-api` 的
`postgres,web-embed` 编译检查；不运行测试、服务、数据库连接或浏览器流程，也不重建发布包。
首次针对 `auction-config`、`auction-setup`、`auction-web-admin` 的 all-features Clippy 在
PostgreSQL-only 依赖组合下遇到既有 `auction-storage/src/database/admin_mail/backfill.rs:37`
的 `infallible_destructuring_match`，不在此次设置页范围内修改；上述工作区全 feature 门禁通过
不表示这个窄 feature 组合的问题消失。
本轮后端收紧继续使用 `just verify`、`auction-admin-api` 的 `postgres,web-embed` 编译检查和
`git diff --check`；HTTP 并发、元数据错误、发布后的同步失败和进程中断路径未做行为或故障注入验证，
需要用户明确恢复测试范围后再补运行证据。
