# Agent Note: 无配置首次启动与管理页初始化

Status: implemented

## Problem

手工部署要求操作者先准备真实敏感 TOML 和两个站点 origin。首次部署需要在无配置状态进入
管理页，先输入数据库、管理员、基础和进阶参数，再生成对应配置并继续部署。正常 Admin 启动
会先读取角色 TOML、数据库和 runtime 文件，因此不能仅在已有管理路由加一张表单；配置缺失时
业务状态根本无法装配。

独立设置入口继续由本文拥有，配置模板与发布内容的收敛见
[发布包范围决定](../simplification/2026-09-18-release-artifact-scope.md)。文档重建笔记只规定
文档门禁，没有功能重叠。
数据库的五项输入、编码和兼容边界由[连接参数决定](2026-09-18-database-connection-fields.md)拥有。

## Decision

`auction-admin-api` 在无参数、无显式 `AUCTION_CONFIG_FILE` 且没有现有角色配置时，先于
`AppConfig` 装配进入一次性初始化模式；已有或显式指定但损坏的配置始终失败关闭。发布制品也可
通过 `setup --output-dir <绝对路径>` 指定配置输出目标。初始化进程仅监听
`127.0.0.1:8091`，终端打印高熵一次性令牌；普通 Admin HTTP 不注册 `/setup` 或初始化 API。
管理端 Dioxus `/setup` 页面不经过业务会话外壳，只向令牌保护的接口提交数据库五项参数、管理员账号
密码、两个精确 origin 和有限的基础/进阶参数。

`auction-setup` 拥有独立 HTTP 门禁和数据库连通性检查；`auction-config` 从通用配置模板物化
三角色、公共、敏感和共享 runtime TOML，并让三个角色的正式 loader 校验完整目录。
输出先写在同一父目录的私有临时目录中，目标已存在时拒绝覆盖；成功后整体发布。数据库
连接检查不建库、不迁移，敏感输入与底层错误不进入响应或日志。操作者以实际服务账号启动
初始化二进制，准备运行目录、用户组和 unit 后执行严格部署预检；数据库迁移、启动顺序和
readiness 继续由 `auctionctl deployment` 拥有，Caddy 仍须人工审阅和 reload。

## Alternatives considered

1. **在正式 Admin router 增加未认证 setup 页面。** 复用路由和监听最少，但普通服务会暴露新
   写入口，且无配置时仍无法构造业务状态；故采用独立初始化表面。
2. **让安装器通过 shell 提示输入全部字段。** 不需新 Web 页面，但无法满足管理页设置需求，
   复杂进阶参数和错误恢复也会退化为终端脚本。
3. **自动创建 PostgreSQL 数据库并在保存时迁移。** 看似更一键，但需要高权限数据库凭据，
   且会把不可逆迁移混入可重试的表单提交；因此只做连通性检查，迁移仍归部署控制器。
4. **允许初始化覆盖已有配置。** 可复用表单作重配置入口，但会破坏已部署密钥、runtime
   指纹和回滚证据；现有配置修改继续走受认证的管理页及受控运维流程。

## Consequences

新主机可以在不准备任何 TOML 的情况下打开本机管理设置页并生成完整配置；保存后由操作者
执行既有严格预检与启动链。代价是首次部署仍需预先创建 PostgreSQL 18 数据库/应用账号，远程浏览器
需 SSH 隧道，Caddy import/reload 和目标主机备份仍由操作者负责。页面只提供高频初始参数；其余
非敏感高级运行配置由正式 Admin `/config` 页面在登录后编辑。已存在配置、显式路径错误和无
`postgres,web-embed` 的制品不会自动开放初始化。当前只执行静态门禁与发布构建，没有创建真实
数据库、运行行为测试或声称线上验收完成。
