# Agent Note: 全库文档重建与静态维护边界

Status: implemented

## Problem

项目原有 37 份正式 Markdown 文档。根 README 与架构说明混合大量实现补记，模块 README 缺少清晰分节，
配置示例重复在多个位置。默认不编译数据库驱动的事实与启动示例不一致，技术栈还把未实现的 SSE、
Argon2id 和 OpenAPI 描述为现有能力。历史“R1”声明缺少完整原始证据索引，容易被误读为当前生产验收结论。

用户要求重建整个项目文档，并明确使用决策记录技能。目标是让读者找到正确 owner、实际命令和能力边界，
同时保留已有 wire、迁移、安全要求与真实取舍。

## Decision

根 README 只持有产品与阅读入口；[文档导航](../../../../docs/README.md)登记正式文档；
架构负责 owner 与能力矩阵；契约保留编号和精确语义；模块 README 负责源码定位与局部实现细节；
运维手册负责前提、确认、命令、回执与失败处理。现有文档路径保持稳定，重复配置以受版本控制的 TOML 模板为入口。

[状态页](../../../../docs/status.md)区分源码实现、静态检查、历史隔离验证声明和仍缺少的运行证据。
整理文档不新增产品能力、不修改数据库、不运行行为测试，也不覆盖工作区已有无关代码改动。

仓库新增 Rust 静态文档工具，由 [Justfile](../../../../Justfile)及独立 CI 工作流调用。
它检查本地链接、标题锚点、导航覆盖、Cargo 包 README 和活跃笔记结构，不引入 npm、Node 或第二套程序库依赖。
`.gitignore` 仅开放 `.agents/notes/`，其余代理临时文件仍忽略。

## 历史决策审计

重建前检查 `.agents/notes/`、`docs/adr/`、`docs/decisions/` 和正式文档中的笔记引用；这些决策树均不存在，
也没有 proposed/implemented/rejected 笔记命中。因此无须吸收、归档或拒绝已有笔记。
原技术栈、契约和模块文档承载的稳定约束继续保留；有关 Leptos 的历史取舍保留为历史理由，
不把旧安全状态包装成此次核查过的上游现状。

## Alternatives considered

1. **只在原文追加目录与修正段。** 改动最少，容易保留所有旧措辞；但首页继续混合大量实现日志，
   重复配置和验收结论仍有多个维护点，因此重写入口、架构、技术栈并重组细节文档。
2. **完全自动从源码生成所有文档。** 路由、版本和文件清单容易同步；但源码不能独立解释历史格式、
   被放弃方案、运维授权与缺失证据，因此只把可机械检查的事实交给门禁，理由和手册继续人工维护。
3. **直接移植技能的 TypeScript/npm 脚本和看板。** 可复用成熟的笔记检查；但与本仓库全 Rust 及单一构建链约束冲突。
   当前用 Rust 检查实际使用的 Markdown 与活跃笔记格式，归档封印在首次需要归档时另行建立。

## Consequences

读者可以从根入口到达全部正式文档，模块责任、执行前提和证据边界独立呈现。
新增/移动文档以及路径变更会触发静态检查，笔记不再被全目录忽略。
代价是新增一个小型 Rust 文档工具与导航维护职责；它只支持仓库采用的行内相对 Markdown 链接和 ATX 标题，
不代替完整 Markdown 解析器、外链可用性检查或技术语义审查。

既有合同细节和部分实现说明仍较长，后续按 owner 同步，不以文件短小为由删除失败关闭或恢复约束。
真正需要引用式链接、复杂标题语法或归档封印时，应先扩展静态工具及其说明，不能静默跳过校验。

只读源码对照确认：64 条 feature 路径、12 个事件 kind/version 组合、37/12 个后端迁移、
63/29 个 PostgreSQL/SQLite CREATE TABLE 对象均有登记，27 个业务表列宽与组件声明一致。
这些计数只描述此次静态快照，不替代参数组合、SQL 执行或页面运行验证。
开始工作时已有代码改动的文件摘要保持一致；本次不执行服务启动、数据库操作或行为测试。
运行证据缺口继续由状态页显式持有；静态工具不证明生产验收。
