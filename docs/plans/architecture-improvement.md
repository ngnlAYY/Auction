# 架构改进计划

[文档导航](../README.md) · [架构](../architecture.md) · [开发指南](../development.md) · [运维手册](../../ops/README.md)

版本 v1（2026-11-02）。本计划只处理代码与工程体系，不包含线上数据处置；线上问题在各阶段完成并经用户批准部署后自然受益。每完成一个工作项，在[进度](#8-进度)中更新状态。

## 1. 目标与原则

目标：在不削弱现有资金安全与审计保证的前提下，降低外部依赖导致的故障面、减少“例外谓词”式维护、让人工处置以证据为中心，并建立可重复的发布流程。

原则：

1. [协作规范](../../AGENTS.md)的领域不变量全部保持：命令幂等、Serializable 关键事务、追加式事实、结果未知不重发、缓存不决定正确性、冻结策略不改写。
2. 每个工作项一个主题提交，按“领域 → 用例/端口 → 存储/外部适配 → HTTP/Web/Worker”落地，同步契约与运维文档。
3. 默认门禁仍为 `just verify`；行为测试与线上部署都需要用户逐项批准（见[决策事项](#7-需要决策的事项)）。
4. 先可观测、再改行为：每个改变运行行为的阶段，都先有能证明改进效果的指标。

## 4. 分阶段方案

### W0 错误分类与外部请求指标

目的：任何“未持久化错误”都能定位到闭集原因；外部请求的消耗可度量，作为 W1 的验收依据。

| 项 | 内容 | 涉及位置 |
| --- | --- | --- |
| W0.1 | 为 `ApplicationError` 增加 `safe_kind() -> &'static str`，闭集分类（如 `funding_unproven`、`evidence_expired`、`repository_conflict`、`remote_busy`），不含秘密与正文 | `crates/auction-application/src/errors` |
| W0.2 | 43 处丢弃点改为记录 `safe_kind` 与业务标识（obligation/delivery/world），保持原控制流不变 | `crates/auction-jobs/src/worker/**` |
| W0.3 | Worker 指标：`worker_unpersisted_error_total{loop,kind}` | `crates/auction-observability` |
| W0.4 | 外部请求指标：按 world/operation/类别统计请求数、间隔门等待时长、`account_busy`/限流/超时次数、维护与观察耗时及预算耗尽次数 | MoogleMail 客户端与 `mail/poll/cycle.rs` |

验收：`just verify` 通过；新指标在 `/metrics` 可见；错误日志不含秘密（沿用敏感值审查）。

### W1 外部账号调度

目的：单账号配额下，用户可感知的动作（发送、付款证据、收件）优先；账号异常时整体退避；稳态请求量远低于配额。

| 项 | 内容 | 关键约束 |
| --- | --- | --- |
| W1.1 账号忙熔断 | 识别战斗页/冻结后，按账号记录 `busy_until`，退避 1→2→5→10 分钟，期间只放行一次探测；其余请求不发网络、直接返回 `AccountBusy` | 熔断只在内存限流，不决定任何业务状态（不变量 5）；写入类在 sending 围栏前被拒，不产生未知结果 |
| W1.2 诊断去重 | 同一忙碌期只保存首份战斗页；诊断淘汰按类别保留写入未知类证据 | 不降低 write_unknown 证据保全 |
| W1.3 优先级门 | 用分级令牌桶替换 FIFO `IntervalGate`：写入（send/take/return）> 付款与交付证据 > 收件 > 维护 > 观察；低优先级保底份额防饿死；每类有独立预算 | 总速率仍不超过 `minimum_request_interval`；同账号远端写入继续串行 |
| W1.4 增量扫描 | Sent 与 Read Mail 持久化“已完整扫描到的最高 MID + 时间”水位；常规轮只读新增页，候选早于水位时按候选时间有界回扫；每日一次完整校验扫描 | 水位只用于减少读取，不作为发送或收取证明；缺失或不连续时回退完整扫描 |
| W1.5 证据退避 | 履约证据按年龄指数退避（等待领取的邮件从每分钟逐步放宽到 30 分钟），付款截止前后提高频率 | 不改变付款期限与恢复策略 |
| W1.6 配置 | 预算与退避参数进入 `worker.toml`，带中文“可选/必填”注释并同步[配置参考](../../ops/config/README.md) | 默认值保持当前行为上限 |

验收（以 W0 指标度量）：稳态外部请求低于配额 30%；维护 p95 低于 60 秒且无预算耗尽；模拟战斗期每个退避间隔不超过 1 次探测、1 份诊断。

### W2 统一处置事实模型

目的：每个投递/履约终态都有且只有一条可审计的处置事实，读侧只看“未处置”，消除分散的排除谓词。

| 项 | 内容 |
| --- | --- |
| W2.1 领域 | `DeliveryDisposition` 闭集：`auto_sent_proof`、`operator_sent_confirmation`、`admin_failed`、`equipment_loss`、`legacy_self`、`preflight_retired`、`operator_acknowledged`；每类定义准入事实 |
| W2.2 迁移 | 只追加表 `delivery_dispositions`（delivery、fence、kind、来源引用、操作者、原因、时间），追加触发器；同步保留政策与[数据库契约](../contracts/database.md) |
| W2.3 回填 | 迁移内只回填能由既有事实精确证明的行（legacy 自寄可信谓词、装备损失、Admin 失败命令、预检退役元数据、人工 Sent 确认），其余保持未处置 |
| W2.4 写入 | 各写者在原事务内追加处置：Admin 对账、装备损失、`confirm-sent`、提醒预检退役、legacy 修复 |
| W2.5 读侧 | 仪表盘、告警、Admin 列表改用“未处置”视图，删除 `reads.rs` 中的专用排除；新增“确认已处置”命令处理无业务影响的历史失败 |
| W2.6 履约 | 履约终态同理（如装备损失后的线下补偿），避免第二套谓词 |

验收：迁移前后各面板计数与当前排除口径逐项一致（迁移内或预检脚本输出差异）；读侧不再含专用排除谓词。

### W3 规则上移

目的：业务判断在领域/用例层以纯函数表达，可脱离数据库验证；存储层只负责锁序、加载与 CAS 写入。

统一模式：

```text
storage：按锁序加载 → 类型化快照（结构体，而非 JSON Value）
application/domain：evaluate(snapshot) → 允许 / 阻断项闭集
storage：以快照版本做 CAS 写入；数据库函数保留为最后一道约束
```

| 批次 | 目标 | 现位置 |
| --- | --- | --- |
| W3.1 | 人工 Sent 证明准入（两种准入、时间窗、资金占用） | `sent_confirmation/snapshot.rs` |
| W3.2 | 装备损失处置准入 | `equipment_loss/snapshot.rs` |
| W3.3 | 恢复阶段推进（逾期、完成、交付中）收敛为领域状态机 | `recovery_scheduler/scheduler/advance.rs` |
| W3.4 | Admin 投递动作守卫（目击、退役、迁移表） | `delivery_admin/commands.rs` |
| W3.5 | COD 实收资金化校验 | `settlement_funding/receipt.rs` |
| W3.6 | 履约 claim 一致性校验 | `fulfillment_scheduler/claims.rs` |

每批验收：业务规则不再以 JSON 下标表达；Rust 判定与数据库函数在同一组样例上结论一致（W6.2 批准后以集成测试固化，否则以预览输出比对）。

### W4 证据优先的 Admin 运维台

目的：运维在 Admin 内依据 Worker 已采集的证据完成处置，不手工拼证据 JSON、不依赖读懂游戏页面。

| 项 | 内容 |
| --- | --- |
| W4.1 | 投递详情 DTO：尝试历史、冻结期望摘要、Sent 观察与目击、领取状态、处置、关联义务与恢复 |
| W4.2 | Worker 采集的 Sent 详情观察持久化为可引用证据（摘要与回执，不含登录 key 正文） |
| W4.3 | Admin 发起人工 Sent 证明、Admin 失败更正、确认已处置：选择已采集证据 + 原因 + 稳定命令 ID，复用同一应用端口 |
| W4.4 | 对账对话框展示目击与候选；判失败保持闭集原因 |

同步[路由契约](../contracts/routes.md)、五语言译文与前端 `Route`。验收：今天的四类处置（已领取货款、误判失败、结果未知通知、退件重试）均可在 Admin 内闭环。

## 6. 每个工作项的交付规范

1. 开始前 `git status --short`，确认基线分支与工作区干净。
2. 先写清本项保护的不变量与契约变化（路由、JSON、事件、配置、数据库）。
3. 实现后同步契约文档、模块 README、运维文档与配置示例。
4. `cargo fmt --all` 与 `just verify` 通过；涉及数据库的判断在本地 PostgreSQL 18 只读预览核对。
5. 提交标题 `type(scope): summary`，正文写不变量与验证范围；一个主题一个提交。
6. 在[进度](#8-进度)更新状态与提交号。
