# 结算与履约

[docs/README.md](../README.md) · [docs/business-rules.md](../business-rules.md) · [docs/guide/mail-flows.md](mail-flows.md) · [crates/auction-domain/README.md](../../crates/auction-domain/README.md)

一场拍卖从“所有 lot 截止”到“钱货两清”经过四个阶段：**结算计算**（一次事务算出所有金额与义务）→ **履约**（把义务变成邮件并取得证据）→ **投递**（outbox 发信）→ **恢复**（付款超时、拒收等异常）。每一步都持久化、可重放，外部结果不确定时停下转人工，绝不猜测。

## 1. 结算计算

Worker 认领处于 Final 且所有 lot 有效截止都已过去的场次，在一个事务内：关闭活动代理、计算 `SettlementPlan`、写入场次与 lot 结算结果、补偿池流水与全部义务，发布 `auction.settled` 事件。同一场次的结算命令 ID 稳定派生，Worker 重启后继续使用原命令，不会产生第二份结算。

### 金额（HoldCurveV2，新场次默认）

1. **领先比例** `hold_ppm`：获胜者累计领先时长除以“计划开拍 → 计划结束”时长（百万分比，最高 1,000,000）。累计领先从竞价事实计算到 lot 的有效截止，包含软截止延长期；分母仍使用计划时窗。
2. **调整比例** `adjustment_ppm`：在锚点曲线上线性插值。默认锚点：

   | 领先比例 | 0% | 5% | 10% | 15% | 20% | 25% | 30% | 40% | ≥50% |
   | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
   | 调整 | +8% | +6.4% | +4.8% | +3.2% | +1.6% | 0 | −0.4% | −1.2% | −2% |

3. 调整为正：买方额外支付附加费 `floor(成交价 × 调整比例)`，计入税费并注入补偿池。调整为负：形成同额“优惠需求”。
4. **补偿分配**：可用额 = 期初补偿池余额 + 本场附加费合计；每件的补偿 = `floor(可用额 × 本件需求 / 总需求)`，不超过本件需求，尾差留在池中。
5. 结果：**卖方所得 = 成交价**；**买方实付 = 成交价 + 附加费 − 补偿**；期末池 = 可用额 − 已分配补偿。恒等式 `买方实付 + 补偿 = 卖方所得 + 税费` 在每件上成立。

流拍 lot 的所有金额为 0。历史场次若冻结的是 `HoldCurveV1`（历史卖方让利算法，仅供既有快照继续结算、读取与重放）或 `LegacyZeroV0`（无曲线、无补偿池），始终按原策略计算，不补算差额。

### 补偿池

两个世界共用一个补偿池（`compensation_pool` 单行），以 main Credits 计：isekai 成交的买方通过 main 载体 COD 付款，卖方货款也在 main 支付，附加费与补偿进出的都是 main Credits。各世界结算在同一行上串行，余额只由结算与下述冲正改变。

迁移 000071 之前每个世界各有一个池（`settlement_pools`）。合并时两池余额相加成为全局池的起点，`state_version` 从两池最大版本 + 1 起算，并写入审计 `auction.compensation.merge`（含各世界合并前余额与版本）；`settlement_pools` 随后由触发器冻结，作为合并前的期末证据。因此合并前结算的批次，期初与期末是所在世界池的余额。池的范围不属于场次冻结策略：公式与锚点不变，期初余额本就是结算时在锁内读取的运行时输入，所以合并时已创建但未结算的场次直接使用全局池，合并前结算的成交若被撤销，也冲正到全局池。

### 成交撤销冲正（规则 v1）

结算按权责发生制把附加费计入补偿池、把补偿从池中支出。成交随后被撤销时，这两笔金额都不会兑现，必须冲回。恢复记录的 `resolution` 由空首次落定即视为成交撤销：

| resolution | 场景 |
| --- | --- |
| `returned_after_three_cod_returns` | main 装备 COD 达到退回上限，装备退回卖家 |
| `reclaimed` | main 收回装备后确认重列 |
| `cancelled` | isekai 载体 COD 未付款被退回，确认取消并重列 |
| `equipment_recovered` | isekai 已付款但交付被退回，收回装备并向买方全额退款 |

在 `resolution` 落定的同一 Serializable 事务内，锁定补偿池并按冻结的 lot 结算金额冲正：

1. 先把该件的补偿全额退回池中：`可用 = 当前余额 + 补偿`；
2. 再冲回附加费：`冲回 = min(附加费, 可用)`，`期末 = 可用 − 冲回`。余额永不为负；冲回不足的部分（`附加费 − 冲回`）只在余额耗尽时出现，记录在冲正事实中并公开展示，不向后续场次追讨。

冲正写入只追加的 `compensation_pool_reversals`（每个恢复记录、每个 lot 最多一条），同时推进池的 `state_version` 并写审计 `auction.compensation.reverse`。原 `lot_settlements`、`auction_settlements`、`compensation_ledger` 与冻结策略都不改写；这三张表与冲正表由触发器禁止 UPDATE/DELETE。附加费与补偿都为 0（含 `LegacyZeroV0`）时不写冲正。升级到迁移 000070 之前已经撤销的成交不补冲，公开页把它们标为“已撤销（未冲正）”。

### 公开透明

公开站点“补偿池”页（[docs/contracts/routes.md#目录与内容](../contracts/routes.md#目录与内容)）展示：

- 补偿池的当前余额与更新时间；
- 各场批次：期初、税收、折扣需求、补偿支出、实际兑付率（补偿支出 ÷ 折扣需求）、期末与本场冲正净额（有冲正时显示）；
- 展开场次后的逐件明细：成交价、领先比例与时长、调整比例、税收、名义折扣需求、实得补偿、买家实付、卖家所得与冲正（含未冲回金额）。玩家可据此复算上面的公式。

`/api/v1/compensation-pool/{auction_id}/movements` 继续提供逐笔账本（含 `balance_after` 余额链），供第三方核对。

公开站点“履约进度”页（[docs/contracts/routes.md#履约进度](../contracts/routes.md#履约进度)）按已结算场次逐件公开结算后的流程状态：流拍装备是否已寄回卖家，COD 是否已寄出、已过付款期限、被退回或已重寄，异世界装备是否已交付，卖家货款是否已寄出并被领取，以及成交是否已撤销。状态是下文义务、履约与恢复事实的只读投影：每项义务先归为待寄出、已寄出待领取、已完成或处理中，再按装备损失、成交撤销、退件、付款、交付、货款的顺序取首个命中；付款是否完成看付款义务的履约，逾期只看当前付款期限。因此页面显示的是系统已确认的进度：买家已付款但系统尚未确认收款（例如资金门延后收口）时，仍显示待确认收款或付款期限已过，文案只说“尚未确认收款”，不断言买家未付款。当前履约步骤失败或待人工核对，以及成交撤销、退件阶段的恢复阻断，只显示为“处理中”；付款提醒失败也会写入恢复阻断，该阻断被刻意忽略，不改变付款状态。页面不公开原因、邮件或投递信息，也不公开代理模式。接口与补偿池汇总一样为 `no-cache`，每次使用前向源站再验证；Public 页面每次读取可复用 15 秒内的本地缓存，页面另由实时事件和定时轮询刷新（15 秒不是页面状态的新鲜度上限）；读取失败而显示旧结果时，页面会标明那是哪个时间点的结果。

## 2. 履约

Worker 的“结算履约”循环领取可执行义务，按 `pending → prepared → enqueued → satisfied` 推进：

| 阶段 | 内容 |
| --- | --- |
| prepare | 校验收件人当前身份与资格、装备持有、金额与世界；冻结邮件意图（主题、正文、收件人、附件、COD），生成 outbox 投递（prepared） |
| activate | 激活投递，交给投递循环发送（enqueued） |
| reconcile | 读取 Bot 账号的 Sent 记录（必要时还有余额）取得证据：Send 类义务均要求精确匹配的 Sent 领取证据；未领取继续等待。COD／载体付款还须通过后续资金化校验。 |

满足（`satisfied`）后解除依赖它的义务（例如 main 买方付款后、isekai 装备交付完成后，`SellerPayout` 变为 ready）。证据不一致或结果未知时转 `manual_reconcile`，在 Admin“结算报表”中处理。
配置的 Bot 收件名必须与当前认证凭据页面上的玩家名完全一致，才会按内部履约提交。名称不一致时保留冻结收件人并将义务转入 `manual_reconcile`（失败码 `internal_identity_mismatch`）；配置名本身不证明该角色属于当前认证 UID，系统不会重复尝试资金提交或改为外发。

证据未观察时不空转：等待 delivery 终态、Sent 回执或买家/卖家在 MoogleMail 领取资产的延期，按该义务已持久化的延期次数指数放宽（`worker.fulfillment.retry_delay_seconds` 起每档翻倍），最多 10 分钟；COD/货款仍按共享追踪窗口（`evidence_poll_seconds`）对齐读取。货款、退款、流拍/撤拍寄回与异世界交付的邮件已寄出（投递 `succeeded`）而仍未领取时，再按寄出时长（投递完成时刻）分档放宽下一次 Sent 读取：寄出不足 24 小时保持上述节奏，24 小时至 7 天间隔至少 1 小时，7 天以上间隔至少 6 小时。分档只给出最小间隔、只放宽不收紧，配置的追踪窗口更宽时保持原窗口；Sent 找不到与远端读取失败同样适用，本地依赖错误仍按基础间隔重试。COD 与载体付款等的是买家付款，确认后才资金化并解锁卖方货款，因此不参与分档，始终按上述追踪窗口与退避读取：付款截止（`payment_deadline_at`）前后一个上限周期回到基础间隔，迟到付款的确认通常最多延后 10 分钟；追踪窗口配置得更宽时，进入该周期前的一次读取可能按窗口越过它。退避只决定轮询时刻：付款期限、逾期判定与恢复策略都不变；依赖或身份错误仍按配置的基础间隔重试。

结算相关邮件主题带义务 ID，例如 `auction equipment delivery [<义务 UUID>]`、`auction payment request [<义务 UUID>]`、`auction seller payout [<义务 UUID>]`、`auction buyer refund [<义务 UUID>]`。收件人拒收或 COD 过期被退回时，退件由系统发件人 `MoogleMail` 以 `[RTS] ` + 原主题寄回 Bot 收件箱，邮件处理器只在发件人为系统时据去掉前缀后的主题识别为对应义务的退件证据；无前缀的原主题不再识别（义务 ID 可由公开 ID 推出，不能证明来源）。恢复记录付款或交付义务的退件由恢复流程消费；货款、退款与流拍/撤拍寄回的退件留证并建立退件案件，对应未终结履约转人工对账（`settlement_mail_returned`），消费时不自动领取、退回或重发，也不改变资金；之后由 Admin 在案件上选择领回补寄、领回代管或留箱结案（见[docs/guide/mail-flows.md#结算退件](mail-flows.md#结算退件)）。

退件处理与经济义务分开判断：案件结案只表示这次退件已处理完，原权利人的应收不因此消失。领回补寄沿用原义务、原冻结金额与原收件人，只换新派发：货款恢复原 seller 用途、退款恢复原 refund 用途，不重新执行付款分配、不重算税费与补偿，也不再做第二次 seller→refund 转换；资金返还凭精确领回证明只写一次（原分配由 `spent` 回到 `available`，金额仍为 M，补寄时新投递再支出一次，净流出仍是 M），strict_cash 补寄照常经现金门，record_only 不新增余额要求；被冻结的账户可以记录已发生的领回，但不因此解冻或获准补寄。旧派发换代后仍按只追加的历史绑定受资金保护，迟到回调只能重放原“已寄出”结论。领回后代管的现金在偿付报告中计为代管负债，与待付二选一、只计一次，不归为 Bot 自有资金；余额观察早于最近一次现金领回证明时偿付结论为 `unknown`。资产位置互斥：外发在途、退回收件箱（原因 `returned_in_inbox_<义务种类>`）、已领回待补寄、已领回代管（装备按 `custody_<义务种类>` 计入应持）、已领取完成与位置未知（`location_unknown_<义务种类>`）。

新建的 main 装备 COD 邮件正文包含装备名、价格明细（成交价、附加费或补偿、应付金额）与冻结付款期限；isekai 载体付款邮件展示装备名、含载体 Credit 的 COD 面额与同一冻结期限；卖方货款与买方退款邮件写明对应装备名与金额。正文里的付款期限是恢复记录的**首寄期限 D0** = 恢复记录建立时刻（`created_at`）+ 冻结恢复策略版本的付款期限（v1 七天、v2 24 小时），只用于正文呈现，不改变逾期判定。COD 实收资金化与载体付款记账按生成方的同一规则核对这两个展示变量：载荷带装备名或付款期限时，必须等于冻结装备名与 D0 的 UTC 秒精度文本；不带的是加入前生成的旧载荷，按原形状比较；生成方不会产生的组合失败关闭；内部履约的资产冲突门只认这两个变量的已发布形状。各类邮件正文模板保存在数据库，可在 Admin 参数页的“MoogleMail 模板”中定制，已冻结的旧投递保留原载荷，正文缺项时按中性文案呈现。

COD 被退回并由恢复流程重寄时沿用原冻结正文，因此正文里的期限仍是 D0；恢复记录的 `payment_deadline_at` 从重寄时刻按冻结版本重新起算，是实际生效的付款窗口（以恢复报告为准），只决定逾期判定与证据轮询的聚焦时刻。履约对账、实收资金化与载体记账重建期望载荷时一律使用 D0，不读会被重寄改写的 `payment_deadline_at`，不重写载荷、不重算摘要；恢复记录事实不完整或策略版本未知时失败关闭。正文期限因此可能早于实际有效期限。

## 3. 投递（outbox）

所有出站邮件——结算、恢复动作、登录 key、投稿回执、超价提醒、运维告警——都先写入 `deliveries`，再由投递循环发送：

```text
prepared → pending → claimed → sending → succeeded
                                     ├─► failed
                                     └─► manual_reconcile（结果未知）
```

- 领取带租约与 fencing 版本；进入 `sending` 前写入发送尝试摘要，发送后把远端邮件 ID 绑定到投递（唯一）。
- 同类邮件按 `[worker.mooglemail.send_intervals]` 控制发送起点的最小间隔；同一账号的远端写入串行。
- **结果未知时不自动重发**：发送阶段的超时、崩溃或远端响应异常无法证明寄出结果时，投递转为 `manual_reconcile`；过期的 `sending` 租约也先转入该状态。邮箱维护循环会尝试用原发送尝试冻结的完整期望在 Sent 中精确找回邮件；Sent 列表时间只到分钟，开始围栏按原 `sending_at` 所在分钟的起点比较，该分钟内任何同内容、同凭据的其他未绑定尝试都使找回失败关闭。找不到不代表未发送；Admin 可记录失败或明确授权重试，但主动 Send 不允许仅凭手填远端引用执行“确认成功”，成功须由匹配的 Sent 证据恢复。
- **Sent 目击门**：结算发送停在 `manual_reconcile` 且冻结匹配未能找回时，邮箱维护在完整 Sent 列表中不限时间查找同一义务主题（主题带唯一 reference），读取详情确认后在投递上记录 `sent_reference_sighting`（MID 已属其他投递时不记录）。目击不是发送证明，只使 Admin 对该投递的重试与判失败返回 `delivery_sent_sighted`，防止重复付款或把已寄出误判为失败；应在游戏中核对后改用下文 Sent 人工证据确认。Admin 判失败的原因码为闭集 `verified_not_sent`、`recipient_invalid`、`no_longer_needed`，历史失败码保持原样。
- **修复后恢复投递**：先核对原发送尝试、归档响应及后续处置，不能只凭 `write_started=false` 或 Sent 未命中就批量重发。对仍为 `manual_reconcile` 且已明确授权重试的记录，Admin 对账使用最新 `fencing_version` 与稳定命令 ID 执行 `retry`；同一事务把原投递恢复为 `pending`，把关联失败/人工核对履约恢复为 `enqueued`，并恢复相关恢复流程投影，不另建义务或直接修改数据库。重试命令结果未知时原样重放。
- 新的可发送投递在提交后唤醒投递循环：完成插入的进程单独调用 `public.signal_delivery_ready()` 发送空载荷通知，而不是在入队事务内 `pg_notify`；通知失败或进程在发送前崩溃由 Worker 轮询兜底，领取仍只依据租约与 fencing。

## 4. 恢复（付款超时与拒收）

每个已售 lot 在结算时依据场次已冻结的恢复策略建立恢复记录（`RemindV1`，版本决定付款期限）；升级不改写既有场次或恢复记录：

| 规则 | 默认 |
| --- | --- |
| 付款期限 | 从结算建立恢复记录起算：v1 为 7 天；自动排期的赛季前场次冻结 v2，为 24 小时。main COD 收回重寄后按冻结版本重新起算 |
| 逾期提醒 | 1 次（邮件提醒买方） |
| COD 退回上限 `cod_return_limit` | 3（可配 1–10） |

付款期限到达只创建提醒并进入 `payment_overdue`，不会仅凭逾期自动取消成交、退回装备或拉黑买家。实际截止以恢复报告的 `payment_deadline_at` 为准；赛季前场次的配置时序校验使用计划结束时间，软截止或延迟结算后仍从实际建立恢复记录起算完整 24 小时。

- main 装备 COD 在付款前退回：第 1 至 `limit − 1` 次退回时，系统取得收回装备的动作证明后重新寄出原 COD（金额与装备不变）；第 `limit` 次退回时，为卖家建立撤拍退回义务，原 COD 与卖方货款按失败收口，并拉黑买家。每封退件只计数一次。
- 恢复流程只消费来源可证明的系统退件：持久化的发件人恰为 `MoogleMail`，主题是 `[RTS] ` + 该义务种类的 canonical 主题；来源无法证明的历史记录由结算退件消费方隔离，不计次数。证据对象与结算退件消费方共用同一严格模型：邮件处理器按系统后缀记录的原收件人与原正文摘要照常接受，未知键、缺键或越界失败关闭。退件证据须与冻结预期一致：Credits、COD 与附件相符，没有派发引用（恢复记录的付款与交付义务只有首寄），且收件时间不早于结算所在分钟再减 2 分钟时钟余量（收件箱时间只到分钟）、不晚于记录时刻。不符的退件照样消费并计数，恢复记录进入 `reclaiming` 并以阻断码 `evidence_mismatch`（报表显示为 `recovery_evidence_mismatch`）等待人工核对，不建立自动动作；同事务追加审计 `recovery.return_blocked`，`reason` 区分内容不符（`content_mismatch`）与时间越界（`received_outside_window`）。其后的退件照常处理。
- 恢复流程消费了原投递本轮的系统退件之后（恢复记录当前退件指向这封已消费的退件），邮件已回到 Bot，收件人无法再领取：Admin 确认前履约虽仍停在 `enqueued`，看板与告警都不再按等待领取、长期未领取或积压计，后续领回、确认与重寄由恢复流程承担；恢复流程重寄清空当前退件后，新一轮发送重新按等待领取计。
- isekai 载体 COD 退回时先收回载体；载体不自动重寄，收回证明成立后由 Admin 以 `cancelled` 确认取消：退回次数未达冻结上限时不要求拉黑（不改变冻结的处罚阈值），达到上限时仍须先完成既定拉黑。已经付款但交付装备被退回时先取得装备收回证明，再以 `equipment_recovered` 确认。两者确认后都重列到该世界的草稿接收场次，后者还激活买方退款；没有草稿目标时保持 `relist_pending`。main 的 `reclaimed` 只在退回达到冻结上限、拉黑已完成且对应收回证明与义务状态允许时可确认（未达上限由系统自动重寄）。Admin 恢复报告的 `allowed_commands`、导航待办计数与确认事务共用同一规则。
- 赛季换季限制（参与早鸟期的世界）：赛季开始前的新赛季草稿不接收重列，保持 `relist_pending` 并按持久化退避重试；原始投稿收件或成交场次开拍后已经历赛季开始的旧赛季装备永不重列，记录阻断码 `relist_season_closed`（报表显示为 `recovery_relist_unavailable`），停在 `relist_pending` 且不再自动重试，由 Admin 人工处理。判断沿用不可变的原始投稿收件事实，修改场次排期不会把旧装备变为新赛季资产；只使用已冻结且非 NULL 的赛季边界，不回填历史场次。
- 上述任一路径首次落定 `resolution`（成交撤销）时，同事务按[成交撤销冲正](#成交撤销冲正规则-v1)回滚补偿池。
- Admin 确认 `reclaimed` 或 `cancelled` 时，同一事务把原付款履约收口为 `failed`（`recovery_reclaimed` / `recovery_cancelled`），把依赖它且从未开始的卖方货款与 isekai 装备交付收口为 `failed`（`recovery_sale_voided`），并在原付款投递当前 fence 上追加 `cod_returned` 统一处置事实与审计；原投递与发送证明不改写，买方退款保持 `contingent`。原付款已满足、原付款投递仍在准备/排队/发送、原付款投递在当前退件之后又开始发送，或依赖履约已开始执行时拒绝确认，交给人工核对。Admin 确认 `equipment_recovered` 时，已满足的载体付款与资金证明保持不变，同一事务把从未开始、没有投递与支出的卖方货款收口为 `failed`（`recovery_sale_voided`），把已寄出又被收回的交付收口为 `failed`（`recovery_equipment_recovered`），在原交付投递当前 fence 上追加 `recovery_equipment_recovered` 处置与审计，并激活买方退款；原交付须有可信 Sent 证明、对应系统退件已被该恢复记录消费、本轮 Take 的来源邮件、装备、世界与证明摘要精确相符，且没有更新派发或未解决写入，否则拒绝确认。两种确认都要求已消费的退件能把原付款（装备收回为原交付）每一次可能已到达远端的发送逐一归属：一封邮件只会被退回一次，可能外达的发送数必须等于本恢复记录已消费的系统退件数，只有投递当前这次发送能凭明确记录的 `write_started=false`、`outcome_unknown=false` 失败证明未外写；任何发送都必须早于当前退件的截止时刻（恢复记录消费该退件的时刻，与退件收件时刻加 3 分钟——收件箱时间只到分钟、另留 2 分钟时钟余量——两者取早），最早的发送早于第一封退件的截止。退件之前另有可能外达的发送（同一分钟内的多次发送、时钟偏差下落在截止之前的重发，时间都无法区分）或退件之后又有发送时，确认返回 `409 recovery_send_unattributed`，什么都不改，交人工核对；多轮 COD 重寄每轮一次发送对应一封退件，照常确认。计数规则之外另有 Sent MID 补充证明：每一次可能外达的发送都是带 Sent 绑定远端 MID 的冻结发送尝试、MID 数等于已消费退件数时，归属同样成立（每封邮件只退回一次，每个 MID 都对应一封已消费的退件）。Worker 的 COD 自动重寄与达到上限后的自动退回卖家用同一规则（原 COD 在退件之后仍在准备或发送中同样不成立），不成立时不重寄、不撤销成交，以阻断码 `send_unattributed`（报表显示为 `recovery_evidence_mismatch`，具体原因见恢复报告）停在 `reclaiming` 并追加审计 `recovery.send_attribution_blocked`，不占住推进队头；Worker 每 10 分钟按持久事实复核，成立后自动解除并继续推进。原付款投递在退件之前被重新排队、恢复接管后停在待发（从未进入发送围栏）时不阻挡归属：收回、取消与自动退回卖家同事务把它终结为 `failed/recovery_superseded`，自动重寄以新 fence 接替它。口径见[docs/contracts/database.md](../contracts/database.md#结算资金恢复与投递)。退款随后照常领取、经资金转换把卖方用途改为退款用途，再 prepare/activate 寄出；资金转换、资产冲突门、内部履约校验与 funding 预览只认这一精确收口事实，任意其他 `failed` 仍然阻断。原交付的“可信 Sent 证明”在确认收回链、内部退款校验与资产冲突门是同一谓词：投递成功、远端引用已证明，证明为精确载荷（`sent_exact_payload_v1`）、旧格式引用恢复（`sent_recovered_reference_v1`，只为缺冻结发送尝试的旧投递生成）或冻结尝试绑定的自动/人工证明；funding 预览只认确认据此写下的收口事实。成交撤销后，恢复记录的付款、交付与卖方货款义务在履约领取和 prepare/activate/满足的最终事务中都不再执行，确认前领取的旧 claim 随版本变化失败关闭；只有 `equipment_recovered` 之后的买方退款照常执行。Admin 投递台的释放、重试与对账重试也在同一事务内按投递来源义务复核同一资格：成交已撤销、或该投递已不是义务的当前派发时返回 `409 settlement_obligation_ineligible`，不把原投递改回待发送；已提交的同一命令仍先重放原结果。恢复流程接管退件之后（恢复记录已消费付款或交付义务的退件、持有收回证明，或来源可证明的系统退件已到达、尚待消费），原付款与交付投递的重寄只归恢复流程（main COD 未达上限由其自动重寄，其余经 Admin 确认收口），三种动作同样返回该 409；投递 Worker 也不再领取这类投递，已领取的在发送围栏回滚（零 Credits 的 COD 与现金发送同一道门），恢复流程自己的重寄清空当前退件与收回证明后照常发送。迁移 `000112` 只修复能证明确认、退件、Take 与被处置发送尝试彼此一致的历史记录（命令账本有确认；原付款已寄出等待领取且是唯一派发；当前系统退件已被消费并由对应 Take 取回；每一次可能外达的发送都由已消费的退件逐一归属、确认后没有新 fence；依赖未开始），结果未知、确认后新 fence 或新派发等其余记录保持原样留给人工核对。
- 恢复并非单一路径：未付时为 `awaiting_payment`，到期转 `payment_overdue` 并创建一次提醒；main 收款后可完成，isekai 收款后先进入 `delivering_equipment`，交付满足后完成。退件可转 `reclaiming`，经收回、确认后进入 `relist_pending`、`refunding` 或 `completed`。`refunding` 只凭已提交的完成事实结束：买方退款履约已满足（审计 `auction.recovery.refund_completed`），或退款邮件被拒收退回、经退件案件精确领回并代管结案（履约 `failed/settlement_return_held`、案件 `held` 且领回证明已持久化，审计 `auction.recovery.refund_custody_completed`，完成时刻取领回证明时刻）。后者不冒充退款已完成：退款履约、原退款资金用途与代管负债都不改写，原买方的退款权益由代管承接，之后从代管补寄照常经退件案件执行、不受恢复记录已完成影响。Admin 确认必须携带原因、稳定命令 ID 与当前状态版本，所有动作写入审计。

### 隔离邮件交还原 owner

寄售收件无法安全归属、或隔离重检确认邮件属于既有拍卖退件时，解除隔离会把邮件交还原拍卖退件案件或原恢复流程。交接只承接责任：不创建或起写 Take/Return、不补寄、不产生资产 POST、资金分录或寄售 `return_intake`，也不改写原隔离观察与历次观察。原 owner 按原有证据、围栏与状态决定下一步；交还本身不是领回、退回或结案证明。

- 交还原退件案件时以 `return_mail_id` 与原证据引用完成交接；主题里的义务 ID 在本地不存在时 `obligation_id` 可以为空，原案照既有行为以 `unbound/obligation_unknown` 建隔离案件，UUID 只作为证据保留。
- 交还原恢复流程时，资产匹配不是移交门槛：已知付款义务但资产不符的退件仍由原 recovery 消费一次、记 `evidence_mismatch`，不建立资产动作。
- 两种交接都在同一事务补写旧格式 `inbound_mail`（`mail_kind='delivery'`、`status='accepted'`、`decision_code='settlement_recovery_returned'`，ID 按旧公式派生）、`mail_original_links`（inbound、邮箱键、远端 MID、Bot UID、世界与认证观察）与旧 `mail_commands` 完成事实；同键已存在时逐字段核对，任何不一致失败关闭，不覆盖历史行。
- 旧拍卖的直达处理（投稿续办、系统发件人加规范主题的退款留证、建案与重放）不以共享原信 K 映射成功为前提；升级前的在途旧信仍按原路完成。见[docs/guide/mail-flows.md#寄售寄件来信](mail-flows.md#寄售寄件来信)。

### Sent 人工证据确认

当原生 Sent 已证明邮件发出，但附件已领取、历史尝试关联不完整、原生分钟时间不足以通过自动恢复，或该投递已被 Admin 误判为失败时，可以在 Admin 投递详情选择已记录的 Sent 证据并预览。CLI 入口为 `auction-cli settlement confirm-sent <DELIVERY_UUID> --evidence <JSON>`，执行须提供稳定命令 ID、当前 fencing 版本、操作者、原因和逐字确认。Admin 预览分别列出实际触发的责任，包括附件已领取、其他历史尝试尚未绑定，以及更正失败结论时邮件发送分钟早于当前尝试。CLI 按预览接受已有的领取责任和历史尝试责任。CLI 按 MID 读取最近的 Worker 观察，证据文件的参数见 [apps/auction-cli/README.md#sent-人工证据确认](../../apps/auction-cli/README.md#sent-人工证据确认)。

此入口限定 main 结算的单件装备 COD、流拍退回、撤拍退回，以及已有真实收款分配的卖方货款。应用端口匹配原冻结正文、身份、原生发送分钟、金额和附件。未领取的装备要求 Worker 实见清单、冻结清单和本次声明逐件相同。历史观察缺清单时可触发邮箱轮询或等待下一轮 Sent 维护，取得带编号的观察后刷新详情并重新选择证据。已领取的装备需要全零当前资产和匹配冻结名称及 COD 的原生回执，操作者须确认已领取，现存的领取前实见编号也必须匹配。货款必须有 Worker 实见的空装备清单。

现金接受完整正额 Credits、零 COD 与无装备。未领取时原额仍在、回执为空且正文未变。已领取时剩余为零并带原生 `Removed attachment: <千分位金额> Credits` 回执，须显式接受已领取责任。原冻结卖方金额、原收件人及当前 UID 的原 lot/义务/投递 `seller` 分配必须完全一致，分配须为 `unknown`，lot 来源须为 `collected` 且用途仍为 `seller`，原预留命令与资金分录必须存在且匹配。货款冻结载荷按生成方两代口径核对。写明装备名前的旧载荷只有 `reference` 与 `amount`。带 `item_name` 的新载荷，名称必须等于该义务对应装备行的冻结名称。

历史尝试保留，旧尝试关联的人工接受独立记录。被 Admin 对账为失败、且其后再无变化的投递也可用同一入口更正（预览 `corrects_admin_failure=true`）。Sent 分钟须在投递激活后、失败结论前，早于当前尝试时须接受旧尝试关联。原失败命令与审计保留，履约从 failed 恢复正常对账。活跃领取、退休损失投递、已有成功、已返还资金或付款提醒以外的恢复动作均拒绝。

Admin 判失败之后仍可更正的投递，Worker 会在看到对应邮件时读取一次详情作为证据。维护只匹配该轮已读到的 Sent 条目，列表读取失败、未完整取得本轮覆盖范围或在可见条目中命中多封时跳过。人工对账投递优先使用原有的轮转和恢复预算，失败投递使用剩余额度。每个投递与 MID 只能读取一次，已有观察直接跳过，读取失败或取消也不重新获取。观察在当前 fence 下保存，阻止重排，投递和履约仍停在失败状态。超出可见范围、更正成功或不再是当前派发的投递退出补采范围。补采未能取得实见编号时，未领取的装备仍无法确认。

提交追加不可变人工确认，使用独立 `sent_operator_confirmed_v1`，不冒充 `sent_exact_payload_v1` 或设置自动 `sent_verified`。持久证明必须与冻结尝试、MID 绑定及当前投递一致，单独 metadata 标签不能赋予证明能力。Admin 仅填写远端引用仍不能确认主动 Send 成功。原义务与结算金额保持：装备确认后原履约恢复，由 Worker 继续取得真实收取证明、经资金 owner 记账并放行原冻结卖方货款；现金确认则与自动恢复共用资金 owner，在同一事务把原未知支出分配变为 `spent` 并追加一次原投递的支出分录，再恢复正常履约对账，不创建新付款、资金来源或收款凭据。原投递已被系统退件绑定（退件案件已建立）时，邮件已经退回，人工确认与自动恢复都只收口投递与资金占用，不把履约改回等待领取，履约仍归退件案件处理（见[docs/guide/mail-flows.md#结算退件](mail-flows.md#结算退件)）。人工确认不证明收件人已领取；现金金额仍完整附在原已发邮件中。

预览、提交和重放分别输出 `preview`、`committed`、`replayed`。结果未知时保持原命令 ID、证据和全部参数重放核对，不能换 ID 或混入最新预览版本。

### 装备损失人工处置

main 已结算成交的装备在实际寄出前损失时，运维可通过 `auction-cli settlement equipment-loss <LOT_UUID>` 只读预览，再以 `--execute`、稳定命令 ID、操作者、原因、资金账户、三项预期版本、冻结卖方金额与逐字确认记录人工处置。操作步骤与完整参数见 [apps/auction-cli/README.md#装备损失人工收口](../../apps/auction-cli/README.md#装备损失人工收口)。资格由结算 owner 在同一 Serializable 事务内校验：原装备 COD 必须停在库存读取失败的人工核对状态，全部尝试都明确未开始外写，且没有既有收款、活跃领取或冲突恢复/资产操作。Sent 中未找到邮件或单条 `write_started=false` 不能替代这些完整约束。

操作者明确声明装备已损失，并承担买方线下补偿责任；这项声明不证明补偿已支付。系统追加独立人工处置事实，以 `operator_equipment_loss_v1` 证明收口原付款履约，不冒充 Sent 邮件或真实 COD 收款。此入口只支持已就绪的 `record_only` 资金账户，拒绝 `strict_cash`；操作者承担的买方金额与既有补偿按原冻结结算分配，不记为真实 `collected_payment`，不改写原结算金额、策略或补偿流水。

命令在同一事务内终结原投递为 `failed/equipment_destroyed`、收口买方退款执行责任与恢复记录，并解除原 `SellerPayout` 的阻塞。恢复 `stage=completed`、`resolution=NULL`：不再催款、退款或重列，不拉黑买家，也不触发成交撤销冲正。原损失投递永久退休，Admin 对账/重试不能将它复活。卖方仍按原冻结金额通过正常履约工作项与真实邮件支付，人工处置成功并不表示卖方已经收款。

默认 JSON 的 `outcome=preview` 只是只读投影；实际提交返回 `committed`，原 ID 同参数重放返回 `replayed`。结果未知时保持命令 ID、原因、账户、版本和金额等全部原参数重放，由命令账本判定；不能换 ID 或将新预览的版本混入原请求。

## Bot 内部履约与资金账户

当义务的收件人就是 Bot 自己（例如 Bot 账号作为卖家寄售、或作为买家竞得）时，给自己寄信没有意义，也无法从 Sent 取得收款证据。此时履约走**内部分支**：在一个事务内直接满足原义务，同时记录资金用途、审计与依赖解除，不产生 outbox 投递。

| 原义务 | 内部动作 | 需要装备在库 | 需要资金账户 |
| --- | --- | --- | --- |
| `UnsoldReturn`、`WithdrawnReturn` | 直接留存（KeepUnsold） | 是 | 否 |
| `WinnerEquipmentCod`、`WinnerPaymentCarrierCod` | 购买（Purchase） | 是 | 是 |
| `WinnerEquipmentHandoff` | 交接（Handoff） | 是 | 否 |
| `SellerPayout` | 卖方货款留存（RetainSeller） | 否 | 是 |
| `BuyerRefund` | 退款（Refund） | 是 | 是 |

内部身份分支使用当前远端账号 UID、玩家名称与联合证据，并核对配置的 Bot 名称；配置名称不能替代最终的同账号证明。联合证据需要 MoogleMail 与论坛目标资料读取能力，当前 Worker 仅在启用论坛时装配后者。内部动作只选择原义务的执行方式，不重算冻结金额，也不创建新的责任；装备持有在付款前与 isekai 交接时各自重新证明。

### 资金账户

需要资金的内部动作要求全局存在一个 Bot 资金账户（固定于 Main 世界的 Bot UID，Credits 计）。账户有两种模式，建立后不能切换：

| 模式 | 含义 | 建立方式 |
| --- | --- | --- |
| `record_only`（只记账） | 记录结算责任与真实收款，不读取 Bot 余额，不以 Bot 现金限制个人消费 | `auction-cli funds open-record-only` |
| `strict_cash`（真实现金） | 每次支出前观察 Bot 余额，只能动用对账时授权的自有额度与补偿额度；出现账实缺口时新增支出冻结 | `auction-cli funds reconcile` 对账（需专用账号声明） |

账户未建立、未对账、已冻结或资金不足时，相关内部履约保持等待，不会退化为外部邮件。

执行开户或对账写入前必须停止 Worker，并确认全部程序已同版升级：账户一经建立（`ready` 或 `frozen`），所有现金 Send 都必须经过资金门，而 CLI 构建自带的现金门能力只证明当前构建已接线，不能证明线上 Worker 的版本。写入命令取得与 Worker 相同的邮件/论坛凭据所有权并持有到提交结束，期间独占邮件 owner。

建立与对账步骤（只读 `preview` 不访问远端）：

1. `auction-cli funds preview --uid <UID>`：只读查看账户状态、责任投影、阻断项、`preview_digest` 与确认短语模板。
2. 选择模式：
   - 只记账：`funds open-record-only`，携带 `--expected-version 0`、`--preview-digest` 与 preview 给出的确认短语。
   - 真实现金：`funds reconcile`，声明 `--proprietary-credits`、`--compensation-credits`、`--dedicated-account` 与确认短语。
3. 输出 `committed` / `replayed` 才算完成；`outcome_unknown` 时用同一命令 ID 与参数重新执行以核对，不要换 ID。

参数细节见 [apps/auction-cli/README.md#bot-资金](../../apps/auction-cli/README.md#bot-资金)。
