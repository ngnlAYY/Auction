# 业务规则

[docs/README.md](README.md) · [docs/guide/settlement.md](guide/settlement.md) · [docs/guide/mail-flows.md](guide/mail-flows.md) · [docs/guide/forum.md](guide/forum.md) · [docs/guide/player-guide.md](guide/player-guide.md)

本页汇总 HentaiVerse 装备拍卖的业务规则。规则的权威实现位于 [crates/auction-domain/README.md](../crates/auction-domain/README.md)（纯计算）与 [crates/auction-application/README.md](../crates/auction-application/README.md)（用例编排）；本页数值均为默认值，括号中给出对应配置项。

## 世界与场次

- 系统服务两个游戏世界：`main` 与 `isekai`。每个世界独立编号场次（期号），可在 Admin“参数配置”中即时启停。
- 每个场次在创建时**冻结**一份策略快照：经济规则、结算策略与恢复策略。之后修改配置只影响新场次，已有场次永远按冻结快照计算。

### 生命周期

```text
Draft ──► Preview ──► Live ──► Final ──► Settling ──► Settled
  │          │
  └──────────┴──► Cancelled（只允许开拍前取消，须记录原因与操作者）
```

| 状态 | 含义 |
| --- | --- |
| Draft | 草稿：接收邮件投稿的目标场次，目录对外不可见 |
| Preview | 预览：目录公开但不能出价；仍可继续接收投稿（每个世界同一时刻最多一个 Draft 或 Preview 场次接收投稿） |
| Live | 进行中：可以出价与设置代理 |
| Final | 最终阶段：仍可出价；尚未到期且持有人资格有效的 Slow 代理转为快速模式，Fast 代理保持原模式，不能新建 Slow 代理 |
| Settling / Settled | 结算中 / 已结算 |
| Cancelled | 已取消（只能在开拍前） |

### 周排期（`[auction.schedule]`）

周排期默认关闭。启用后 Worker 按 IANA 时区（`timezone`，默认 UTC）为每个参与且已启用的世界（默认 main、isekai）维护场次；常规安排为每周一场，早鸟期可替代常规场次：

| 阶段 | 默认时间 |
| --- | --- |
| 建立草稿 | 上一场开拍时同时建立下一场草稿（或 Worker bootstrap 补建） |
| 开放预览 | 周四 22:00（`preview_day`/`preview_time`） |
| 正式开拍 | 周五 00:00（`open_day`/`open_time`） |
| 计划结束 | 周六 12:00（`nominal_end_day`/`nominal_end_time`） |
| 进入 Final | 最早的 lot 有效截止前 15 分钟（`final_phase_lead_seconds`） |
| 结算 | Final 阶段中所有 lot 的有效截止都已过去 |

- 轮次进入预览后，从计划开拍前 2 小时起暂停该世界的收件轮询，实际开拍后恢复；已预览的轮次取消或被标记错过时也恢复。恢复后的投稿按处理事务锁定的当前接收目标入场，不能仅凭邮件到达时间保证进入本场。
- 每轮的本地时间来源（时区与三个本地钟点）在建立时冻结，夏令时按冻结规则换算，不从当前配置反推。

### 赛季早鸟期（`[auction.schedule.early_bird]`）

默认关闭，仅在周排期启用时生效。赛季开始（默认每年 05-01 与 11-01 的 09:00，早鸟时区默认 UTC）前安排一场赛季前场次，赛季开始后的窗口（默认 7 天）内安排早鸟场次；覆盖期从赛季前场次预览起算（未安排时从赛季开始起算），到早鸟窗口结束与末场计划结束中较晚者为止，替代与该覆盖期重叠的常规周场：

- 赛季前场次（`pre_season_session`，默认开启）：isekai 在赛季开始日关服换季，该场是旧赛季关服前的最后一场。它在赛季开始日前第 `pre_season_days_before`（默认 3）天的 `open_time` 开拍，预览提前量与竞价时长同早鸟场次（默认 D-3 16:00 预览、18:00 开拍、D-2 18:00 结束）。它冻结 24 小时付款期限（恢复策略 v2），配置校验要求计划结束后 24 小时严格早于赛季开始日本地 00:00；物化具体场次与 Admin 修改排期共用同一门禁，按夏令时换算后的实际 UTC 截止及冻结的赛季身份复核，不能通过改期把付款窗口推过换季边界。软截止或延迟结算不会缩短该冻结期限。它按常规品质收件；它开拍时建立首场早鸟草稿。
- 窗口内第 `session_days`（默认第 1、3、5、7 天）天的 `open_time`（默认 18:00）开拍，预览提前 `preview_lead_minutes`（默认 120 分钟，最少 120），竞价持续 `live_minutes`（默认 1440 分钟）。
- 默认只用于 isekai（赛季会清空异世界资产）。首场早鸟草稿建立后至赛季开始前暂停该世界收件（`pause_intake_before_season`），赛季开始后恢复，玩家可在首场预览前投稿；安排赛季前场次时，暂停从它开拍起生效。
- 停止接收装备：窗口内早鸟场次在创建时冻结最早收件时刻（赛季开始）。当前接收目标为该场次且尚未到该时刻时，邮件投稿（整封退回，原因 `season_intake_closed`）、Admin 手工录入与恢复重列都在锁内被拒绝，与是否暂停收件轮询无关；默认从赛季前最后一场开拍、首场早鸟草稿建立起生效。邮件还要求原始收件时刻不早于该下界：旧赛季来信即使延迟到新赛季处理仍整封退回；已经持久接受的投稿重放原决定，不重新判定。赛季开始后，旧赛季装备也不会再被重列（见[docs/guide/settlement.md#4-恢复付款超时与拒收](guide/settlement.md#4-恢复付款超时与拒收)）。升级前已创建的场次不补写最早收件时刻或 24 小时付款策略。
- 窗口内的投稿可按 `qualities` 限定品质（默认不限）。
- 早鸟场次以 `early-bird:YYYY-MM-DD:N` 作为轮次身份，赛季前场次的 N 为 0，窗口内场次从 1 起编号。
- 常规周场与赛季前场次不重叠时两者都保留。例如赛季开始日为周二或周三时，默认周场（周六 12:00 结束）之后仍有赛季前场次。

### 手动操作

Admin 可在“拍卖场次”页对场次执行：进入预览、开拍（预览中且到达计划时间，或配置允许提前开拍）、进入 Final、提前结算（需配置允许并填写原因）、取消（开拍前）、修改排期（仅开拍前）。Admin 手动进入 Final 会把活动 lot 截止改为操作时刻加冻结的 Final 提前量；提前结算则立即关闭竞价入口，由 Worker 后续结算。Admin 与 Worker 使用同一套生命周期服务与排期日历，开拍时按日历建立下一场草稿。

## 投稿（寄售）

卖家把装备作为附件、以主题 `auction` 发 MoogleMail 给 Bot。系统读取装备详情并校验后接受，再收取附件；不合格时整封退回并说明原因。完整规则见[docs/guide/mail-flows.md#拍卖投稿](guide/mail-flows.md#拍卖投稿)：

- 邮件只能包含装备附件；附带 Credits、COD 或其他物品整封退回。
- 装备必须可交易，品质达到门槛（默认 Legendary、Peerless），并通过可选的前后缀/分类/类型/等级过滤。
- 起拍价默认 50,000 Credits（邮件默认值，`[worker.mooglemail] start_price`），可在正文中用 `start <金额>` 统一指定或用 `<装备链接> start <金额>` 逐件指定，金额支持 `k`/`m` 后缀。
- 投稿进入该世界当前接收投稿的草稿或预览场次；参与早鸟期的世界在赛季开始前停止接收装备（见[赛季早鸟期](#赛季早鸟期auctionscheduleearly_bird)）。

Admin 也可在后台手工录入装备（需要 `equipment_data_key`）。草稿状态的 lot 可以撤下或修改起拍价。

## 用户与登录

- 玩家以主题 `register` 发不带资产的邮件注册（正文任意）：系统以发件人游戏名建立账号，并回信发送 43 字符的**登录 key**。已注册玩家再次发送会重新获得 key（找回）。
- 玩家以主题 `rekey` 发不带资产的邮件可自助轮换登录 key：系统以发件人游戏名找到账号，轮换 key 并在同一事务内注销该账号全部有效会话，再回信新 key；未注册、被拉黑或身份冲突时回信说明。旧 key 与旧会话立即失效，玩家需用新 key 重新登录。
- `register` 与 `rekey` 各自按账号每 24 小时只回信一次；超出的请求仍记录命令与审计但不回信。账号类邮件带资产、拒收说明与换绑结果等说明信按发件人每 24 小时最多 10 封，超出时不寄说明信，但附带资产照常退回。
- 改名后以主题 `rebind`、正文为旧 key 发邮件，把账号名称更新为新的发件人名称。
- 登录 key 通过回信交付；服务端保存摘要与加密信封，发送时按需解密。Admin 可以重新签发或吊销 key。
- 登录时长由账号偏好决定：默认永久，可设固定期限；单账号并发会话数上限 10（`max_public_sessions`）。满额时新登录不会再被拒绝：在同一事务、同一用户行锁内把最久未活动的有效会话标记为已注销（保留记录、登录 key 不变），再建立新会话；被注销的设备用原登录 key 重新登录即可，并在 Public 站点看到“已在其他设备登录”的提示。
- 在论坛回帖出价的玩家若没有对应账号（按已绑定的论坛账号 ID，或不区分大小写的同名账号匹配），系统会按论坛账号建立一个只能通过论坛参与、不能登录网站的账号；该玩家之后用同名游戏角色发 `register` 邮件即可取得登录 key。

### 黑名单

被拉黑的账号不能出价（`bidder_ineligible`）。拉黑由 Admin 执行，或在买家 COD 被退回达到上限时由恢复流程自动执行；黑名单在公开站点可查。拉黑与解禁对寄售订单的影响见[一口价挂单](#一口价挂单)的受限权利与拒收处罚。

## 竞价

- **金额网格**：出价与代理上限必须是 1,000 Credits 的正整数倍，且不超过 1,000,000,000。
- **最低可出价**：无人出价时为起拍价；之后为当前价加增量。增量 = 当前价按 5%（`bid_increment_ppm`）计算后向上取整到 1,000 的倍数，至少 1,000（当前价先按千位向上折算）。
- 新建场次冻结竞价策略 v2：各类出价使用相同的最低增量计算，自动代理触及授权上限时允许上限出价（见下文）。已创建场次继续冻结的 v1 规则，历史出价和命令重放不重新计算。
- **软截止**：每个 lot 有独立的有效截止时间。出价若在截止前 15 分钟内（`soft_close_window_seconds`）被接受，截止延长到“接受时刻 + 15 分钟”（`soft_close_extension_seconds`），只延后不提前。截止后的出价被拒绝。
- 已领先的玩家不能给自己加价；已有生效代理的玩家不能再普通出价。
- 出价与代理操作还要求世界已启用、场次处于 Live 或 Final、lot 仍在竞价且未到有效截止，参与用户处于 active 且未被拉黑；自动代理反击也重新核对持有人的资格。
- 每次被接受的出价都是只追加的事实，带接受后的截止时间与版本号；竞价日志公开可查。

## 代理竞价

代理授权包含上限与模式，系统在上限内自动为玩家反超：

| 模式 | 行为 |
| --- | --- |
| Fast | 被超越时立即按当时最低可出价反超，触及代理上限时直接以上限出价 |
| Slow | 被超越后等待 10 分钟（`proxy_slow_interval_seconds`），到期重算最低可出价并受代理上限约束；Final 阶段不能新建 |
| FinalFast | 进入 Final 时由有效 Slow 代理转换，不再等待；原有 Fast 代理保持 Fast |

- v2 的自动反击金额为 `min(当时最低可出价, 代理有效上限)`，结果必须严格高于当前价。最低加价触及或超过上限时直接以上限出价，只有无法严格反超时才耗尽，不同价守位。例如当前 105,000、完整最低价 111,000、代理上限 110,000 时，代理出 110,000；上限仅 105,000 时则耗尽。普通出价仍必须达到完整最低价，新建代理的上限也不能低于创建时的最低价。
- 新代理与已有代理竞争时，较高上限获胜，同上限由更早授权者优先；按较低上限加本场完整增量计算竞争价，再受胜者上限约束。竞争只追加胜者的一笔出价，未成交的授权上限不是出价事实；最终价格仍必须达到竞争前的最低可出价。创建代理的上限也须达到该最低值。Slow 代理（包括正在等待反击的）与新代理竞争时同样当场决出，胜者立即出价。
- 竞价日志在胜者这笔出价上公开落败授权的出价人与上限，页面把它按落败者的一次代理出价排在胜者出价之前，用来说明竞争价从何而来，否则会像胜者自己连续抬价。快慢模式一样处理，模式本身不公开；生效中代理的上限，以及被普通出价超过上限而耗尽的代理上限，都不公开。
- 生效中的代理只能**降低**上限：领先时不低于当前价，等待反击时不低于冻结策略要求的下一口；被超越耗尽后可以重新设置，新上限必须高于上一份。
- 持有人失去竞价资格时，其生效代理被冻结，不再反击并清除慢速调度。
- 既有 v1 场次保留固定 +1,000 反击、对手恰好触及代理有效上限时同价守位，以及代理竞争取较低上限 +1,000 并受胜者上限约束的规则；不自动升级其冻结策略。
- 同一玩家在同一 lot 设置代理的次数上限默认 3（`proxy_max_outbid_uses`，0 为不限）。
- 网站新建代理表单的初始模式取本场冻结的 `proxy_default_mode`（Final 阶段不能新建 Slow 时为 Fast），玩家可以切换；提交的授权总是显式携带模式。
- 本场可整体关闭代理（`proxy_enabled = false`）。
- 论坛回帖只支持普通出价，代理只能在网站设置。`<lot 代码> start` 是以起拍价开出尚无出价的 lot 的普通出价（非整千的历史起拍价向上取整到 1,000 网格）；lot 一旦有出价，它就低于最低价而被拒绝，写法见[docs/guide/forum.md#回帖出价语法](guide/forum.md#回帖出价语法)。

## 装备标记与提醒

登录玩家可以标记关注的 lot，并在账号偏好中分别开关 MoogleMail（`mm`）与论坛私信（`pm`）提醒：都开时同一被超事件在两个渠道各发一条，都关时标记只作收藏、不产生提醒（偏好的 wire 值见[docs/contracts/routes.md#会话与账户](contracts/routes.md#会话与账户)）。标记者在该 lot 上从领先变为被超越时，系统按已启用的渠道发送提醒——每个渠道在每个连续领先周期最多一次，自己加价不会开启新周期。提醒**不合并、不限额**。被超提醒在 MoogleMail 出队顺序中的位置见[docs/guide/mail-flows.md#出站邮件](guide/mail-flows.md#出站邮件)。

普通出价（网站或论坛回帖）与新建代理会在提交后自动标记该 lot。开启论坛私信提醒（`pm` 或 `both`）要求论坛同步已启用且账号已绑定论坛账号；不满足时偏好接口拒绝保存（`422`）并提示，不会静默丢弃提醒。

持有人有慢速代理且被超越时代理仍可反击：只记录待定提醒、不入队；代理反超成功即作废；代理耗尽（到期无法反超、进入 Final 时无法反超，或等待期间被更高普通出价击败）时在同一事务入队；截止前仍未定的待定提醒按有效截止退役。

提醒的发送资格只到该 lot 的**有效截止**（含软截止延长）。截止后尚未开始发送的提醒在发送围栏前退役：MoogleMail 投递记为预检拦截的未发送失败（`lot_watch_invalidated`），论坛私信队列记为 `suppressed`/`source_invalid`；两者都不会补发其他邮件。已经进入发送围栏的提醒不受影响。论坛私信由独立队列发送；两个渠道结果未知时都只做人工对账，不重发。

## 结算

拍卖结算后，每个已售 lot 产生成交价、买方实付、卖方所得、税费与补偿，并生成需要履约的义务。规则摘要（详见[docs/guide/settlement.md](guide/settlement.md)）：

- 卖方收到成交价全额（HoldCurveV2）。
- 买方根据**领先时长比例**调整：领先时间越短附加越多（最高 +8%），领先超过 25% 后转为优惠（最多 −2%）；附加费进入补偿池，优惠由补偿池按比例支付。
- 两个世界共用一个以 main Credits 计的补偿池（isekai 成交同样在 main 以 Credits 付款与支付货款）。成交事后被撤销（买方未付款、退回卖家或退款）时，同事务冲正：补偿退回池中、附加费冲回（最多冲至余额为 0）；结算结果、账本与冲正都只追加并在公开页逐件展示。
- main 世界：装备以 COD 寄给买方，买方收取时支付。isekai 世界：先在 main 发一封附带 1 Credit 的载体邮件，COD 面额为买方实付 +1 Credit（收取载体后净支付为买方实付），确认付款后在 isekai 交付装备。
- 卖方货款在买方付款后支付（isekai 要等装备在 isekai 交付完成）；流拍与撤拍的装备寄回卖方。

## 付款超时与恢复

- 付款期限从结算建立恢复记录时起算 7 天（赛季前场次为 24 小时），到期未付款时创建一次提醒。
- main 装备 COD 退回并取得收回证明后：前 `cod_return_limit − 1` 次（默认前 2 次）重新寄出原 COD；第 `cod_return_limit` 次（默认第 3 次）把装备退回卖家并拉黑买家。isekai 载体或交付装备的退件走取消/收回确认、重列及必要退款流程，见[docs/guide/settlement.md#4-恢复付款超时与拒收](guide/settlement.md#4-恢复付款超时与拒收)。
- 结果不确定的外部操作（例如邮件是否寄出）一律转为人工对账，由 Admin 在结算报表与投递队列中处理。

## 一口价挂单

玩家为自己持有的一件装备登记一个固定标价。每条挂单属于一位卖家、一个世界、一件装备、一种模式，标价以 main Credits 计。这项服务默认关闭，由运营开启后可用。已提供登记、解析与展示、寄件预约、整封收件与隔离、代管、运营止售、软关闭、季前撤回通知与季末关闭，以及购买、资金与派发、撤回寄还、退件、处罚、受限权利与灭失办理；整封接受与退回在取得/退回验证器签收后启用（见下）。

- **两种模式**（登记后不可更改）：`direct`（非寄售）只做展示，装备留在卖家手里，买卖双方在游戏内自行联系，平台不经手装备与货款；`consigned`（寄售）先登记，再把装备寄给平台代管，卖出后由平台交付装备并把货款寄给卖家。
- **装备身份**是“世界 + 装备编号”：世界只有 main 与 isekai，编号是不带前导零的正十进制数（最多 32 位）。与本站历史记录比较时只在同一世界内进行，把旧记录的编号去掉前导零后逐字比较，不转成数值；全零、带符号或含非数字字符的旧编号不代表任何装备。

| 状态 | 含义 |
| --- | --- |
| `resolving` | 已登记，正在读取并核对装备 |
| `displayed` | 非寄售，已公开展示 |
| `awaiting_deposit` | 寄售，已核对，等待寄来装备 |
| `deposit_accepted` | 整封接受已完成，平台承担取得或核对责任；尚未首次上架 |
| `available` | 已取得实物且挂牌决策通过；后续购买入口可用的唯一可购买态，第 4 期尚未提供购买 |
| `held_off_market` | 已代管但暂不上架；第 4 期产生运营止售（`operations_hold`）、复核（`review`）、卖家不具资格（`seller_ineligible`）、服务停用（`service_disabled`）与额度已满（`quota_blocked`），付款与季末原因留给后续车道 |
| `withdrawal_pending` | 已上架挂单登记了撤回意愿，停止销售，等待后续撤回合同执行 |
| `sale_pending` | 已有成交合同、履行中；留给后续车道 |
| `rejected`、`expired`、`closed` | 终态；不可恢复，重新登记是一条新挂单 |

挂单的事实每变化一次，版本加 1。代管实物另有 position 状态 `awaiting_take`、`in_custody`、`committed`、`in_transit`、`reconcile`、`handed_over`、`season_ended`、`lost`；第 4 期只产生 `awaiting_take` 与 `in_custody`，其余由后续车道产生。

- **核对通过才公开**：装备必须可交易（灵魂绑定的装备两种模式都不能登记），当前持有人必须是登记人。本站对这件装备有历史记录时，还要求历史责任已经了结，且最后一位已证实的持有人就是登记人：仍在拍卖或交付途中、返还尚未取得证明的判为占用中；证据不足以确定接收人的判为历史不足；最后持有人不是登记人（包括在平台外转手）的判为持有人不符；多条历史记录互相矛盾的判为历史冲突。
- **强制终止**（针对未代管的活动态 `resolving`、`displayed`、`awaiting_deposit`，多项同时成立时按下列顺序取原因）：这件装备进入了拍卖（登记之后新建的 lot）→ `closed / auction_lot_created`，之后流拍也不恢复，装备按拍卖的正常流程处理；卖家失去资格 → `closed / seller_ineligible`，解禁后不恢复；服务停用 → `closed / service_disabled`；到达当前状态的期限 → `expired`。期限从进入该状态时起算：解析 24 小时，展示默认 30 天，待寄默认 7 天；到达期限的那一刻即失效，改价不延长期限。
- **寄件预约**：寄售挂单核对通过进入 `awaiting_deposit` 后，卖家在本人寄件指引页签发预约码 `C1-<43 字符 base64url>`。预约码只在本人页面内存中出现，不进回执、审计或日志；有效期取 `reservation_ttl_hours`（默认 24，1–168），且不晚于待寄期限与冻结的季末界。每个挂单至多一个有效预约，重新签发会让该挂单的旧预约失效。卖家以主题 `consign`、正文只逐行写预约码（最多 20 件、2048 字节，无自由文本、空行或重复码）寄给 Bot，发件人游戏名必须与登记卖家一致。
- **整封接受、退回与隔离**：一封寄件按原信整体决定，任一逐件不合格即整封退回，不拆开接受。全部通过时，预约逐件消费、逐件 item 与代管 position 在同一事务建立，整封恰一个 Take 处置；可证明原样退回时恰一个 Return 处置；确定没有资产时归档且不建立处置工作。证据不足、重复编号、别名歧义、未知附件、身份或回执能力不能证明等按隔离处理：保留原观察、责任与重读键，零资产外写；重检只读原信，解除后转为接受/退回/归档，或交还原拍卖退件案件/原恢复流程。**当前生产收件就绪的取得与退回能力均未签收（`take_ready=return_ready=false`），需要 Take 或 Return 的整封一律按 `take_unproven`/`return_unproven` 隔离，由运营处理；签收后本段接受与退回规则才生效。** 签收需要维护者提供两世界多件寄件详情、Take 前后与系统 Return 回执的真实脱敏样本，现状见[Worker 装配](../apps/auction-worker/README.md#一口价挂单)。完整流程见[docs/guide/mail-flows.md#寄售寄件来信](guide/mail-flows.md#寄售寄件来信)。
- **交还旧 owner**：隔离邮件交还原退件案件或原恢复流程时只承接责任、零资产动作；兼容 `inbound_mail` 补写与两支的细节见[docs/guide/settlement.md#隔离邮件交还原-owner](guide/settlement.md#隔离邮件交还原-owner)。
- **卖家与运营操作**：未代管的活动态可以改价（提交相同价格不产生新版本）与取消（`closed / seller_cancelled`）。已代管的挂单，卖家可登记撤回意愿：尚未上架时保留在 `deposit_accepted`，已上架时转入 `withdrawal_pending` 并停止销售，已下架时保留原原因；寄还原物见下文“撤回寄还”。运营可以对未代管挂单下架（`closed / admin_delisted`，另附只对运营可见的说明）；已代管的挂单可设置运营止售，转入 `held_off_market / operations_hold`，解除止售后保持 `held_off_market / review`，不自动重新上架。写操作携带 `command_id` 与预期版本。
- **软关闭**：把 `[consignment] enabled` 改为 `false` 停止新登记、签约与首次接受；已经决定的 Take/Return、已登记撤回意愿与存量处置继续；已成交订单的首次派发、补寄、退件领回与订单复核也照常进行（续办旧权利），新购买在购买入口截止。关闭后新的运营止售返回 404，解除止售不受影响；路由口径见[docs/contracts/routes.md#v2-api](contracts/routes.md#v2-api)。Worker 在关闭但有存量时仍运行存量循环，条件见[Worker 装配](../apps/auction-worker/README.md#一口价挂单)。
- **标价与手续费**：标价是 1 至 1,000,000,000 的整数 Credits，不套用竞价的金额网格。手续费率以基点表示（0–9999）：寄售默认 500（5%），非寄售固定为 0。手续费为 `floor(标价 × 费率 / 10000)`，卖家所得为标价减手续费（例：标价 101、费率 500，手续费 5，卖家所得 96）。登记时冻结计价版本与费率；登记请求带上卖家当时看到的费率，与当前适用值不同时拒绝，由卖家重新确认。
- **季前通知**：isekai 季窗与换季提醒同源，取排期日历的时区与换季日期，并按 `isekai_preclose_days`（默认 3，1–90）提前 N 个**本地日历日**的 00:00 换算 UTC 作为预停点。到达预停点后，该季窗内仍非终态、且尚未收到 `preclose_withdrawal` 通知的每个 position 都会收到一封季前撤回通知；预停后新取得的代管件在下一轮补通知，不要求一次性快照。通知正文在建立投递时按冻结季窗生成并冻结，只写季末 UTC 时刻与“在拍卖网站的寄售页面撤回”的说明，不含预约码、装备 key 或任何凭据；收件人取卖家在 isekai 的角色名。通知走通用 MoogleMail Send 投递，外部结果未知时转人工对账，不自动重发。**寄售季前通知不受任何 `send_classes` 分类开关控制**；它属于结算节奏（`settlement`），与资产退回和履约动作无关。
- **季窗只冻结一次**：同一 `(world, season_id)` 以首次提交的冻结界为准，之后即使日历版本、时区或 `isekai_preclose_days` 改变也不改写、不另插新版本；配置变化从下一季生效。迟跑的季任务不能延长既有冻结界。没有可用日历或日历构造失败时不冻结新季窗，isekai 季态保持 `unknown`，新预约失败关闭；已冻结季窗的存量任务照常运行。
- **季末关闭**：到达冻结季末后，Worker 关闭该 isekai 世界中登记时刻早于季末、仍处于旧季市场流程的非终态挂单（成交后正在履行的合同不在此列，继续按原义务处理）。季末前已交付的继续清偿卖款；季末清空的装备不赔偿。关闭后原挂单的 position 仍保留既有事实，后续期别处理旧季代管责任。
- **第 5 期边界（类型化结算，不接单）**：结算义务的来源是拍卖或寄售合同，二者恰一。寄售成交合同（Sale）固定三条义务（main）或四条（isekai），撤回合同（Withdrawal）只有一条无金额的 `withdrawn_return`；卖家所得 S = 成交价 P − floor(P × 费率 / 10⁴)，不套用拍卖的补偿池。这一期只交付合同、义务图、专用领取原语与来源隔离，**没有任何生产调用方创建合同**：购买在第 6 期，因此玩家不能下单，通用拍卖领取与告警不会看到寄售义务。事实详见[数据库契约](contracts/database.md#一口价挂单)与[结算与履约](guide/settlement.md#义务)。
- **受限权利**：成交与撤回合同成立时为冻结受益人登记受限权利（买方续办订单，卖方领取货款或撤回寄还的装备）；代管件另有卖家的撤回权利，损失案件开案时卖家得到只读的案件权利。可执行的动作由服务端按当时的订单事实给出，表结构见[数据库契约](contracts/database.md#寄售损失受限权利与通知迁移-000137)。被拉黑不剥夺既有订单的权利：已成交的订单继续向冻结受益人履约，拉黑只阻断新购。寄出前核对受益人的身份连续性，只认当前用户名与冻结身份逐字相同；改名后冻结名可能已属于别人，站内改名记录也不能证明是游戏内同一角色，所以改名一律判为连续性未证：保留权利、不寄出，转人工核对。
- **拒收与处罚**：可信的系统退件被接管时形成拒收事实，同一拒收周期内达到阈值即形成处罚；处罚待执行期间买家不能新购，执行后账号被拉黑（账号已因其他原因被拉黑时只记录，不再追加黑名单历史）。isekai 未付载体的退件目前只记为待判事实、不计入处罚：退件发生时原合同是否仍可交付没有可读的持久事实。解禁时关闭旧周期、开启新周期，旧周期尚未执行的处罚作废；没有寄售拒收周期的用户解禁，行为与以前相同。
- **撤回寄还**：撤回合同成立的同一事务建立寄还邮件的首轮：收件人是合同冻结的卖家，邮件只附这件装备，不带 Credits、不收 COD。首次寄出时代管件转为在途，卖家领取后撤回完成。寄还邮件被系统退回并经精确领回后，装备回到平台代管，挂单保持撤回状态，不重新上架、不再出售；系统不会自动再寄（补寄只用于未付的 COD 原件），由运营处理。
- **未付取消后的迟到付款**：购买已按买家未付取消并封闭后，迟到的 COD 付款不再记为这笔订单的实收，不写收据、不计入成交资金；钱若已到账，留作该资金账户未归属的实收，由现金对账转人工处理。数据库另有守卫兜底，见[数据库契约](contracts/database.md#寄售损失受限权利与通知迁移-000137)。
- **卖款放行与退款**：卖款只在买家付款经实收认证、且买家确领原件之后放行（main 的原件就是 COD 邮件本身，isekai 另寄原件交割，确领后放行），放行的同时挂单成交关闭、代管件记为已交付；之后系统自动建立卖款邮件（只带卖家所得 S，不收 COD）。退款在转为退款（卖家所得与手续费转为成交价 P）的同时激活，系统随后寄出只带 P 的退款邮件；已转退款的订单不再寄出 isekai 原件。受益人领取 Credits 须有可验证的领取证据才记为已领取。main 订单 COD 认证即视为买家已收件、订单完成，此后再转出的退款不会自动寄出，转人工处理。原件确领与现金领取的验证尚未签收前，这两步都不会自动推进。
- **偿付口径**：寄售成交只在买家付款经实收认证后计入偿付负债，每笔最多计成交价 P 且只计一份：卖款未寄出时计退款义务 P，卖款已寄出只计卖家所得 S，已转为退款计 P，原件已被领取计 S。

## 规则与关于文档

玩家可见的规则文档与“关于”文档（各五种语言）只在 Admin 编写：分别在“规则内容”和“关于内容”页编辑、校验、发布，内容直接写入数据库，没有文件导入路径。两种文档共用同一套机制，按（文档种类，语言）各自独立：每篇有自己的版本号，发布须带上所依据的版本（版本不符即拒绝），同一发布命令重放返回原结果，每次发布追加一条审计记录。公开端按界面语言读取，缺少该语言时回退到英文；规则缺失按服务不可用处理，“关于”尚未发布则显示空状态。

新建的数据库自带一份预置规则：迁移 `000107` 把 2026-11-13 线上发布的五种语言规则文档写入数据库（版本 1，发布者 `system`），只在该语言还没有规则时写入，已有规则的库不受影响。预置内容只是起点，之后照常在 Admin“规则内容”页修改；“关于”没有预置内容。
