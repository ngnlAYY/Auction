# 业务规则

[文档导航](README.md) · [结算与履约](guide/settlement.md) · [邮件流程](guide/mail-flows.md) · [论坛](guide/forum.md) · [玩家指南](guide/player-guide.md)

本页汇总 HentaiVerse 装备拍卖的业务规则。规则的权威实现位于 [auction-domain](../crates/auction-domain/README.md)（纯计算）与 [auction-application](../crates/auction-application/README.md)（用例编排）；本页数值均为默认值，括号中给出对应配置项。

## 世界与场次

- 系统服务两个游戏世界：`main` 与 `isekai`。每个世界独立编号场次（期号），可在 Admin“参数配置”中即时启停。
- 每个场次在创建时**冻结**一份策略快照：经济规则、结算策略与恢复策略。之后修改配置只影响新场次，已有场次永远按冻结快照计算。

### 生命周期

```text
Draft ──► Preview ──► Live ──► Final ──► Settling ──► Settled
  │          │
  └──────────┴──► Cancelled（只允许开拍前取消，须记录原因与操作者）
```

| 状态 | 含义 |
| --- | --- |
| Draft | 草稿：接收邮件投稿的目标场次，目录对外不可见 |
| Preview | 预览：目录公开但不能出价；仍可继续接收投稿（每个世界同一时刻最多一个 Draft 或 Preview 场次接收投稿） |
| Live | 进行中：可以出价与设置代理 |
| Final | 最终阶段：仍可出价；尚未到期且持有人资格有效的 Slow 代理转为快速模式，Fast 代理保持原模式，不能新建 Slow 代理 |
| Settling / Settled | 结算中 / 已结算 |
| Cancelled | 已取消（只能在开拍前） |

### 周排期（`[auction.schedule]`）

周排期默认关闭。启用后 Worker 按 IANA 时区（`timezone`，默认 UTC）为每个参与且已启用的世界（默认 main、isekai）维护场次；常规安排为每周一场，早鸟期可替代常规场次：

| 阶段 | 默认时间 |
| --- | --- |
| 建立草稿 | 上一场开拍时同时建立下一场草稿（或 Worker bootstrap 补建） |
| 开放预览 | 周四 22:00（`preview_day`/`preview_time`） |
| 正式开拍 | 周五 00:00（`open_day`/`open_time`） |
| 计划结束 | 周六 12:00（`nominal_end_day`/`nominal_end_time`） |
| 进入 Final | 最早的 lot 有效截止前 15 分钟（`final_phase_lead_seconds`） |
| 结算 | Final 阶段中所有 lot 的有效截止都已过去 |

- 轮次进入预览后，从计划开拍前 2 小时起暂停该世界的收件轮询，实际开拍后恢复；已预览的轮次取消或被标记错过时也恢复。恢复后的投稿按处理事务锁定的当前接收目标入场，不能仅凭邮件到达时间保证进入本场。
- 每轮的本地时间来源（时区与三个本地钟点）在建立时冻结，夏令时按冻结规则换算，不从当前配置反推。

### 赛季早鸟期（`[auction.schedule.early_bird]`）

默认关闭，仅在周排期启用时生效。赛季开始（默认每年 05-01 与 11-01 的 09:00，早鸟时区默认 UTC）前安排一场赛季前场次，赛季开始后的窗口（默认 7 天）内安排早鸟场次；覆盖期从赛季前场次预览起算（未安排时从赛季开始起算），到早鸟窗口结束与末场计划结束中较晚者为止，替代与该覆盖期重叠的常规周场：

- 赛季前场次（`pre_season_session`，默认开启）：isekai 在赛季开始日关服换季，该场是旧赛季关服前的最后一场。它在赛季开始日前第 `pre_season_days_before`（默认 3）天的 `open_time` 开拍，预览提前量与竞价时长同早鸟场次（默认 D-3 16:00 预览、18:00 开拍、D-2 18:00 结束）。它冻结 24 小时付款期限（恢复策略 v2），配置校验要求计划结束后 24 小时严格早于赛季开始日本地 00:00；物化具体场次与 Admin 修改排期共用同一门禁，按夏令时换算后的实际 UTC 截止及冻结的赛季身份复核，不能通过改期把付款窗口推过换季边界。软截止或延迟结算不会缩短该冻结期限。它按常规品质收件；它开拍时建立首场早鸟草稿。
- 窗口内第 `session_days`（默认第 1、3、5、7 天）天的 `open_time`（默认 18:00）开拍，预览提前 `preview_lead_minutes`（默认 120 分钟，最少 120），竞价持续 `live_minutes`（默认 1440 分钟）。
- 默认只用于 isekai（赛季会清空异世界资产）。首场早鸟草稿建立后至赛季开始前暂停该世界收件（`pause_intake_before_season`），赛季开始后恢复，玩家可在首场预览前投稿；安排赛季前场次时，暂停从它开拍起生效。
- 停止接收装备：窗口内早鸟场次在创建时冻结最早收件时刻（赛季开始）。当前接收目标为该场次且尚未到该时刻时，邮件投稿（整封退回，原因 `season_intake_closed`）、Admin 手工录入与恢复重列都在锁内被拒绝，与是否暂停收件轮询无关；默认从赛季前最后一场开拍、首场早鸟草稿建立起生效。邮件还要求原始收件时刻不早于该下界：旧赛季来信即使延迟到新赛季处理仍整封退回；已经持久接受的投稿重放原决定，不重新判定。赛季开始后，旧赛季装备也不会再被重列（见[结算与履约](guide/settlement.md#4-恢复付款超时与拒收)）。升级前已创建的场次不补写最早收件时刻或 24 小时付款策略。
- 窗口内的投稿可按 `qualities` 限定品质（默认不限）。
- 早鸟场次以 `early-bird:YYYY-MM-DD:N` 作为轮次身份，赛季前场次的 N 为 0，窗口内场次从 1 起编号。
- 常规周场与赛季前场次不重叠时两者都保留。例如赛季开始日为周二或周三时，默认周场（周六 12:00 结束）之后仍有赛季前场次。

### 手动操作

Admin 可在“拍卖场次”页对场次执行：进入预览、开拍（预览中且到达计划时间，或配置允许提前开拍）、进入 Final、提前结算（需配置允许并填写原因）、取消（开拍前）、修改排期（仅开拍前）。Admin 手动进入 Final 会把活动 lot 截止改为操作时刻加冻结的 Final 提前量；提前结算则立即关闭竞价入口，由 Worker 后续结算。Admin 与 Worker 使用同一套生命周期服务与排期日历，开拍时按日历建立下一场草稿。

## 投稿（寄售）

卖家把装备作为附件、以主题 `auction` 发 MoogleMail 给 Bot。系统读取装备详情并校验后接受，再收取附件；不合格时整封退回并说明原因。完整规则见[邮件流程](guide/mail-flows.md#拍卖投稿)：

- 邮件只能包含装备附件；附带 Credits、COD 或其他物品整封退回。
- 装备必须可交易，品质达到门槛（默认 Legendary、Peerless），并通过可选的前后缀/分类/类型/等级过滤。
- 起拍价默认 50,000 Credits（邮件默认值，`[worker.mooglemail] start_price`），可在正文中用 `start <金额>` 统一指定或用 `<装备链接> start <金额>` 逐件指定，金额支持 `k`/`m` 后缀。
- 投稿进入该世界当前接收投稿的草稿或预览场次；参与早鸟期的世界在赛季开始前停止接收装备（见[赛季早鸟期](#赛季早鸟期auctionscheduleearly_bird)）。

Admin 也可在后台手工录入装备（需要 `equipment_data_key`）。草稿状态的 lot 可以撤下或修改起拍价。

## 用户与登录

- 玩家以主题 `register` 发不带资产的邮件注册（正文任意）：系统以发件人游戏名建立账号，并回信发送 43 字符的**登录 key**。已注册玩家再次发送会重新获得 key（找回）。
- 玩家以主题 `rekey` 发不带资产的邮件可自助轮换登录 key：系统以发件人游戏名找到账号，轮换 key 并在同一事务内注销该账号全部有效会话，再回信新 key；未注册、被拉黑或身份冲突时回信说明。旧 key 与旧会话立即失效，玩家需用新 key 重新登录。
- `register` 与 `rekey` 各自按账号每 24 小时只回信一次；超出的请求仍记录命令与审计但不回信。账号类邮件带资产、拒收说明、换绑结果与论坛回执等说明信按发件人每 24 小时最多 10 封，超出时不寄说明信，但附带资产照常退回。
- 改名后以主题 `rebind`、正文为旧 key 发邮件，把账号名称更新为新的发件人名称。
- 登录 key 通过回信交付；服务端保存摘要与加密信封，发送时按需解密。Admin 可以重新签发或吊销 key。
- 登录时长由账号偏好决定：默认永久，可设固定期限；单账号并发会话数上限 10（`max_public_sessions`）。满额时新登录不会再被拒绝：在同一事务、同一用户行锁内把最久未活动的有效会话标记为已注销（保留记录、登录 key 不变），再建立新会话；被注销的设备用原登录 key 重新登录即可，并在 Public 站点看到“已在其他设备登录”的提示。
- 在论坛回帖出价的玩家若没有对应账号（按已绑定的论坛账号 ID，或不区分大小写的同名账号匹配），系统会按论坛账号建立一个只能通过论坛参与、不能登录网站的账号；该玩家之后用同名游戏角色发 `register` 邮件即可取得登录 key。

### 黑名单

被拉黑的账号不能出价（`bidder_ineligible`）。拉黑由 Admin 执行，或在买家 COD 被退回达到上限时由恢复流程自动执行；黑名单在公开站点可查。

## 竞价

- **金额网格**：出价与代理上限必须是 1,000 Credits 的正整数倍，且不超过 1,000,000,000。
- **最低可出价**：无人出价时为起拍价；之后为当前价加增量。增量 = 当前价按 5%（`bid_increment_ppm`）计算后向上取整到 1,000 的倍数，至少 1,000（当前价先按千位向上折算）。
- 新建场次冻结竞价策略 v2：各类出价使用相同的最低增量计算，自动代理触及授权上限时允许上限出价（见下文）。已创建场次继续冻结的 v1 规则，历史出价和命令重放不重新计算。
- **软截止**：每个 lot 有独立的有效截止时间。出价若在截止前 15 分钟内（`soft_close_window_seconds`）被接受，截止延长到“接受时刻 + 15 分钟”（`soft_close_extension_seconds`），只延后不提前。截止后的出价被拒绝。
- 已领先的玩家不能给自己加价；已有生效代理的玩家不能再普通出价。
- 出价与代理操作还要求世界已启用、场次处于 Live 或 Final、lot 仍在竞价且未到有效截止，参与用户处于 active 且未被拉黑；自动代理反击也重新核对持有人的资格。
- 每次被接受的出价都是只追加的事实，带接受后的截止时间与版本号；竞价日志公开可查。

## 代理竞价

代理授权包含上限与模式，系统在上限内自动为玩家反超：

| 模式 | 行为 |
| --- | --- |
| Fast | 被超越时立即按当时最低可出价反超，触及代理上限时直接以上限出价 |
| Slow | 被超越后等待 10 分钟（`proxy_slow_interval_seconds`），到期重算最低可出价并受代理上限约束；Final 阶段不能新建 |
| FinalFast | 进入 Final 时由有效 Slow 代理转换，不再等待；原有 Fast 代理保持 Fast |

- v2 的自动反击金额为 `min(当时最低可出价, 代理有效上限)`，结果必须严格高于当前价。最低加价触及或超过上限时直接以上限出价，只有无法严格反超时才耗尽，不同价守位。例如当前 105,000、完整最低价 111,000、代理上限 110,000 时，代理出 110,000；上限仅 105,000 时则耗尽。普通出价仍必须达到完整最低价，新建代理的上限也不能低于创建时的最低价。
- 新代理与已有代理竞争时，较高上限获胜，同上限由更早授权者优先；按较低上限加本场完整增量计算竞争价，再受胜者上限约束。竞争只追加胜者的一笔出价，未成交的授权上限不是出价事实；最终价格仍必须达到竞争前的最低可出价。创建代理的上限也须达到该最低值。
- 生效中的代理只能**降低**上限：领先时不低于当前价，等待反击时不低于冻结策略要求的下一口；被超越耗尽后可以重新设置，新上限必须高于上一份。
- 既有 v1 场次保留固定 +1,000 反击、对手恰好触及代理有效上限时同价守位，以及代理竞争取较低上限 +1,000 并受胜者上限约束的规则；不自动升级其冻结策略。
- 同一玩家在同一 lot 设置代理的次数上限默认 3（`proxy_max_outbid_uses`，0 为不限）。
- 本场可整体关闭代理（`proxy_enabled = false`）。
- 论坛回帖只支持普通出价，代理只能在网站设置。

## 装备标记与提醒

登录玩家可以标记关注的 lot，并在账号中选择提醒渠道：MoogleMail（`mm`）或论坛私信（`pm`），同一事件只走一个渠道。标记者在该 lot 上从领先变为被超越时，系统按所选渠道发送提醒——每个连续领先周期最多一次，自己加价不会开启新周期。论坛私信由独立队列发送，结果未知时只做人工对账，不重发。

## 结算

拍卖结算后，每个已售 lot 产生成交价、买方实付、卖方所得、税费与补偿，并生成需要履约的义务。规则摘要（详见[结算与履约](guide/settlement.md)）：

- 卖方收到成交价全额（HoldCurveV2）。
- 买方根据**领先时长比例**调整：领先时间越短附加越多（最高 +8%），领先超过 25% 后转为优惠（最多 −2%）；附加费进入补偿池，优惠由补偿池按比例支付。
- 两个世界共用一个以 main Credits 计的补偿池（isekai 成交同样在 main 以 Credits 付款与支付货款）。成交事后被撤销（买方未付款、退回卖家或退款）时，同事务冲正：补偿退回池中、附加费冲回（最多冲至余额为 0）；结算结果、账本与冲正都只追加并在公开页逐件展示。
- main 世界：装备以 COD 寄给买方，买方收取时支付。isekai 世界：先在 main 发一封附带 1 Credit 的载体邮件，COD 面额为买方实付 +1 Credit（收取载体后净支付为买方实付），确认付款后在 isekai 交付装备。
- 卖方货款在买方付款后支付（isekai 要等装备在 isekai 交付完成）；流拍与撤拍的装备寄回卖方。

## 付款超时与恢复

- 付款期限从结算建立恢复记录时起算 7 天（赛季前场次为 24 小时），到期未付款时创建一次提醒。
- main 装备 COD 退回并取得收回证明后：前 `cod_return_limit − 1` 次（默认前 2 次）重新寄出原 COD；第 `cod_return_limit` 次（默认第 3 次）把装备退回卖家并拉黑买家。isekai 载体或交付装备的退件走取消/收回确认、重列及必要退款流程，见[结算与履约](guide/settlement.md#4-恢复付款超时与拒收)。
- 结果不确定的外部操作（例如邮件是否寄出）一律转为人工对账，由 Admin 在结算报表与投递队列中处理。

## 规则文档

玩家可见的规则文档（五种语言）由 Admin 在“规则内容”页编辑、校验、发布，也可用 `auction-cli rules import` 从目录导入。
